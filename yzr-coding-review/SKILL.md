# yzr-coding-review

把代码 review 约束成**发现可追溯、结论可执行**的产物

## 输入与输出

**输入**(任一形态): 代码段 / 文件路径 / git diff / patch(只 review 改动)/ 项目根目录 + 范围

**输出**: 两种形态(对话式分析回答 / 报告形态)+ 逐条过子循环,路由见 Step 3

## 执行原则

1. **不主动改文件**: 产出是结论 / 报告,用户点头后才走具体重构
2. **每条发现可追溯**: 每条发现映射到至少 1 个 catalog 规则名
3. **审视边界收敛**: 不越界到 bug 修复 / 性能调优执行 / 安全审计(发现这些信号时指出"建议另行
   专项处理",不展开);机械可判定项(风格规则 / 格式 / TODO / 文档字符串)归 CI,不占发现项
4. **产物留在对话内**: 报告 / 结论不落成文件,不主动持久化(落文件即成无人维护的第二真源)

### 评审立场

- **资深工程师标准**: 按生产代码的维护成本审,每条发现给直接结论 + 理由,不为照顾情绪放水
- **敢于质疑框架**: 问题根因在抽象层 / 模块划分而不在局部写法时,明确指出"局部重构不够,建议结构性调整"并给出方向。不给完整新设计(那是重写,越界)
- **回到存在理由**: 每条判断先问这段代码为什么存在、服务什么场景、删掉 / 合并损失什么;catalog 是召回清单,不是套用模板
- **洁癖但克制**: 高标准不等于凑数:琐碎发现合并报或放入"不报告项",主表保信噪比

## 工作流

### Step 1: 收集代码

解析输入,确定语言 + 行数;行数 > 500 时与用户确认分段粒度(按文件 / 按类 / 按函数)

### Step 2: 走 catalog 补充

必读 `ref/catalog.md`(规则清单);agent 用其中的重构规则 + 合理性审视规则补齐设计层问题。
数值阈值项(函数长度 / 嵌套层数 / 参数个数等)先现场 grep / AST 速算拿客观计数,再对照规则内的阈值判断,
不凭目测;重复块检测跑 `tools/dup_scan.py`(精确 / `--fuzzy` 近似两模式)拿候选组,报不报由 agent 按规则裁

### Step 3: 形态路由

默认进 **对话式分析回答**(Step 4);用户明确要报告或大范围体检(多文件 / 遗留代码)时进 **报告形态**(Step 5);形态可中途切换

### Step 4: 对话式分析回答(默认)

1. **理解复述**: 先用 2-4 句向用户讲清这段代码**在做什么**(功能意图)与**怎么做到的**(结构 / 控制流),拿不准处显式说"这里我理解为 X,若不对请纠正"。**为什么**: 理解偏了,后面所有发现都是空转;用户纠正理解时,基于纠正重审再列发现,不硬撑原判断
2. **结论先行**: 一句话给出"有没有优化空间"(没有就说明理由,收尾)
3. **列要点**: 按代码位置顺序(file:line);发现 ≤ 3 条直接给全(位置 + 规则名 + 问题 + 建议);
   超过 3 条给全量简表(每条一行)
4. **收尾问询**: 发现多时问"逐条过一遍还是出一份完整档报告";逐条过按代码位置顺序逐条呈现,每条等用户表态:
   - **确认**记为"接受",下一条
   - **改判**按用户意见修正内容,下一条
   - **跳过**记为"跳过",下一条
   - **追问**展开讲清该条后再回到该条表态
5. 逐条过完全部后输出汇总(接受 / 改判 / 跳过 计数 + 采纳清单),询问是否出完整档报告或进入具体重构

### Step 5: 报告形态

开头先给一段**整体理解**(口径同 [章节](#step-4-对话式分析回答默认) 的"理解复述",不超过一段),再按 `ref/report-template.md`
两档输出;末尾问用户要不要追问 / 跳过 / 改判 / 切对话逐条过

## 参考样例

**简短示例:逐条过**。用户输入:

> 陪我一起 review 一下 src/parser.py,逐条过

skill 第一条:

> **1/4** parser.py:1 `函数粒度`:`process()` 62 行内嵌 3 个语义段
> (计算总价 / 校验 / 打印),建议抽 `calc_total()` 和 `validate_order()`。接受 / 改判 / 跳过?

用户: 跳过,后面 3 行是核心逻辑。
skill: 记下,下一条:**2/4** …(循环至汇总)
