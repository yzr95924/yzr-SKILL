# 多模型评审编排

用户显式要求多模型 / 交叉评审才启用本文件；多模型只替换 Step 2 的发现生产，Step 3-5 机制不变，
呈现层的分组与来源标注由[章节](#合并)增补

**存在理由**：多评审员读同一份卷宗出发现，共识与分歧都能显式化；成本随票数线性涨，所以是显式 opt-in

## 名单与校验

默认名单 SSOT 在 `tools/run_multi_review.py` 的 `DEFAULT_ROSTER`，宣布与可用性校验用
`python3 tools/run_multi_review.py --dry-run`（从 skill 根运行；不建卷宗不 spawn）

| 情形 | 处置 |
| --- | --- |
| 用户点名模型 | 点名覆盖默认；模糊名用 harness 的模型发现能力解析成精确 ID，一名多候选列出让用户挑、不静默代选；解析不到时如实报告并列现存相近候选，不拿替身凑数；精确 ID 经 `--models a,b,c` 传入脚本 |
| 未点名 | 直接用默认名单，不再确认往返（默认名单即预确认）；spawn 前在同一条消息里宣布 `--dry-run` 打印的名单与票数，有成本数据时随名单宣布成本，没有时以票数代成本 |
| 名单失效 | 脚本经 `opencode models` 逐个校验，有不可发现即停下报告相近候选，交用户裁定，不静默替换、不静默减票 |

## 编排

1. 物化：被审对象若是粘贴代码，先写成快照文件（系统临时目录下）；输入是 git diff / patch 时，
   把 diff 输出物化成 `change.diff` 快照文件作被审对象（与 SKILL.md 输入口径"只 review 改动"一致，
   评审员审 diff 不审全文件）；磁盘文件用原路径
2. 跑一条命令（从 skill 根运行；目录只收默认代码扩展名，非代码文件如 `change.diff` 须显式列路径才入卷宗）：
   `python3 tools/run_multi_review.py --target <路径...> [--models <id,...>]`。
   脚本一次完成建卷宗（全体评审员收到字节级相同）、并行逐票、调用失败重试一次、逐票契约机检
   （告警不作废，口径见[评审员契约](reviewer.md)的产物节），产出 `<卷宗目录>/reviews/*.md`
   与 stdout 逐票状态
3. **编排者不评审**：主 agent 上下文含主对话、与评审员不对称，亲自评审会击穿同一性保证；当前会话模型
   要入票须显式点名并同样走脚本
4. 回退：CLI 不可用或名单校验失效（脚本停下并报告）时如实告知并退回单模型现状；部分票重试后
   仍败的用余下有效票照常合并并披露逐票状态，全部票失败同样退回单模型现状，不凭记忆补发现
5. 每票审全文、不分段：跨段问题（跨文件重复块、结构性缺陷）是全文评审的固有意义；Step 1 的分段粒度只用于
   合并后的呈现批次

## 合并

对脚本逐票状态标 ok 的输出（`reviews/*.md`）按序处置；带契约机检告警的票（如无发现行）不
强行解析成发现：如实披露该票状态，重跑与否征询用户：

1. 对比理解复述：某份核心意图明显跑偏时，该份降权（其发现不计入共识、保留时标注来源于降权票），
   并在结论写明降权原因；重跑只作为选项征询用户，不擅自重跑
2. 同位置（行号 ±2 内）、同规则名且语义指向同一问题的发现归并为一条，记来源模型集合；
   位置相邻但处置对象不同（如抽函数 vs 提常量）不并：机械套 ±2 会吞掉可执行信息；
   引用评审员原文作证据时逐字，不翻译、不转写
3. 分级呈现：共识（≥2 模型）独立成组排前，其后列单模型发现并标"仅 X 提出"；各组内按代码
   位置排序（与 Step 4"按代码位置顺序"的口径在此衔接）；映射不到 catalog
   规则名的发现由编排者尝试映射，映射不上按审视边界收敛原则过滤或标存疑，不进主表
4. 冲突（同一位置给出互斥处置，如一方判抽函数、另一方判内联）单列"分歧"：对话式排在单票组后
   独立成组，报告形态入主表并在问题列开头标"分歧：A 判 X，B 判 Y"（呈现口径同第 5 条），
   不静默裁决；编排者给资深工程师倾向，最终交用户表态
5. 来源标注落在现有输出格式内（列口径见[报告模板](report-template.md)）：对话式在规则名后附
   `【A+B】` / `【仅 X】`；报告形态写进问题列开头
6. 有效票仅 1 时如实声明"多模型实际退化为单票"，该票清单直接进 Step 3，不分组、不标来源
7. 合并后的清单进 Step 3-5
