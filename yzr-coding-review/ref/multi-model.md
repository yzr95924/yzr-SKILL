# 多模型评审编排

用户显式要求多模型 / 交叉评审才启用本文件；多模型只替换[章节](../SKILL.md#step-2-走-catalog-补充)的发现生产，其余步骤机制不变，
呈现层的分组与来源标注由[章节](#合并)增补

**存在理由**：多评审员读同一份材料出发现，共识与分歧都能显式化；成本随票数线性涨，所以是显式 opt-in

**机制铁律**：评审员票一律由 harness 的 subagent 产生，不起 `opencode run` 之类 CLI 子进程
（那等于在脚本里重造 harness 原生的并行与送达，还要随每次 CLI 版本漂移修脚本）。
用户显式要求多模型评审即构成逐票指定 model 的显式授权

元数据，宽关键词检索只用于解析模糊名

| 情形 | 处置 |
| --- | --- |
| 用户点名模型 | 点名覆盖默认；模糊名按上述方式解析成精确 ID，一名多候选列出让用户挑、不静默代选；解析不到时如实报告并列现存相近候选，不拿替身凑数 |
| 未点名 | 直接用默认名单，不再确认往返（默认名单即预确认）；spawn 前在同一条消息里宣布名单与票数，有成本数据时随名单宣布成本，没有时以票数代成本 |

## 编排

1. 物化：粘贴代码写成快照文件（系统临时目录下，保留原语言扩展名）；git diff / patch（命令输出或
   粘贴文本）物化成 `change.diff` 快照作被审对象（与 SKILL.md 输入口径"只 review 改动"一致，
   评审员审 diff 不审全文件）；磁盘文件用原路径。行号口径：diff 输入按源文件新版行号；快照输入
   按快照文件行号，引用时注明快照口径。目录展开只收默认代码扩展名、vendor 目录剪枝
   （口径同 `tools/dup_scan.py`），非代码文件（如 `change.diff`）须显式列路径才入材料清单
2. 扫描候选落盘：从 skill 根跑 `python3 tools/dup_scan.py <被审路径...>`（另跑一次加 `--fuzzy`），
   输出存成文件（与快照同目录；磁盘被审对象落系统临时目录的会话专属目录）；机械扫描由编排者跑一次，
   各评审员读同一份落盘结果、不自行重跑
3. spawn：名单每个模型一票，用 harness 的 subagent 工具**一条消息并行发起全部票**。逐票 prompt
   全同：角色句（"你是 N 名独立评审员之一。只读下方材料清单列出的文件，按评审员契约规定的角色、
   评审立场与产物顺序，在回复正文直接产出最终评审，最终回复即交付物"）+ 对象说明（被审对象；不转述
   主对话里的用户评价与怀疑点，避免锚定各票）+ 绝对路径清单（被审代码全文 / 快照、`change.diff` 如有、
   dup_scan 候选文件、[评审员契约](reviewer.md)、[规则清单](catalog.md)）。票间唯一差异是模型参数，
   取名单表的精确 ID；**同源即相同**：各票读同一路径，输入同一性由同源保证，无需构造字节级副本
4. **编排者不评审**：编排者上下文含主对话、与评审员不对称，亲自评审会击穿同一性保证；不对称在
   上下文不在模型名，会话模型在名单内时照常入票
5. 回退：harness 无可指定 model 的 subagent、或评审员读盘不可用时如实告知，退回单模型现状；部分票
   失败的用余下有效票照常合并、以名单为分母逐票披露状态，全部票失败同样退回单模型现状，不凭记忆补发现
6. 每票审全文、不分段：跨段问题（跨文件重复块、结构性缺陷）是全文评审的固有意义；[章节](../SKILL.md#step-1-收集代码)的分段粒度
   只用于合并后的呈现批次

## 合并

对每票输出先按[评审员契约](reviewer.md)的产物节核对（复述段、发现行、引用文件在清单内且行号对得上
现文）再处置；不合契约的票（复述段缺失 / 发现行格式不符）不强行解析成发现，如实披露该票状态
（重跑口径见第 1 条）；零发现是合法结果，照常披露、不进降权与重跑处置：

1. 对比理解复述：某份核心意图明显跑偏时，该份降权（其发现不计入共识、保留时标注来源于降权票），
   并在结论写明降权原因；重跑只作为选项征询用户，不擅自重跑
2. 同位置（行号 ±2 内）、同规则名且语义指向同一问题的发现归并为一条，记来源模型集合；
   位置相邻但处置对象不同（如抽函数 vs 提常量）不并：机械套 ±2 会吞掉可执行信息；
   引用评审员原文作证据时逐字，不翻译、不转写
3. 分级呈现：对话式按共识组（≥2 模型）在前、单模型组（标"仅 X 提出"）在后，各组内按代码位置
   排序；报告形态不分组、统一进主表按位置排序（与[章节](../SKILL.md#step-4-对话式分析回答默认)的
   "按代码位置顺序"口径衔接）；某票声称同一问题出现 N 处而编排者仅能核验部分时，不因此降出共识，
   存疑即标注交用户；映射不到 catalog 规则名的发现由编排者尝试映射，映射不上按审视边界收敛
   原则过滤，不进合并清单
4. 冲突（同一位置给出互斥处置，如一方判抽函数、另一方判内联）单列"分歧"：对话式排在单模型组后
   独立成组；报告形态入主表、按[报告模板](report-template.md)列口径在问题列开头标注，不静默裁决；
   编排者给资深工程师倾向，最终交用户表态
5. 来源标注落在现有输出格式内：对话式在规则名后附 `【A+B】` / `【仅 X】`；报告形态列口径见
   [报告模板](report-template.md)
6. 有效票仅 1 时如实声明"多模型实际退化为单票"，该票清单直接进[章节](../SKILL.md#step-3-形态路由)，不分组、不标来源
7. 各票的"不报告项"不合并不标来源：报告形态由编排者聚合进"不报告项"节，对话式不呈现
8. 合并后的清单进[章节](../SKILL.md#step-3-形态路由)起的工作流
