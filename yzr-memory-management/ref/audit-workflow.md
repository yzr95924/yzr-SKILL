# 治理 audit 的执行细节

> 本文件承载[章节](../SKILL.md#治理-audit)的全部执行细节

## Step 1：机械层（lint）

跑 `python3 tools/memory_lint.py <项目根>`（在目标项目里跑时，用绝对路径指向本 skill 安装处的
memory_lint.py），拿到 ERROR / WARN / INFO 清单。机械层只报事实，不做删除判决

## Step 2：判断层（只报现象与候选，判决归用户）

对 WARN 项与各条目逐类检查（事件驱动复核只查 scope 命中条目，见该项）：

- **事件驱动复核（主判据）**：`git log --since` 取近期变更涉及的路径，与条目 scope 匹配，只复核命中的条目——问"这次变更是否推翻 / 改变了它"。规则不随时间腐烂、随事件腐烂，全量按时间扫是噪音
- **吸收检查**：条目关键词 grep AGENTS.md / README / docs / 代码；命中即列删除候选，标注被哪里吸收
- **矛盾检查**：同主题多条观点冲突、或与 AGENTS.md 冲突：只报现象标存疑；需文本外证据才能定的，不下删除判决
- **重复合并**：索引语义比对同主题 → 合并提案，指明并入哪条
- **空泛检查**：摘要写不出具体内容的条目 → 改写或降级提案

## Step 3：治理动作三级阶梯

对每个候选取最轻的足够一级（压缩够就不降级，降级够就不删）：

1. **压缩**：正文并进摘要，条目变短但保留
2. **降级**：文件条目降为索引行（删文件、留一行）
3. **删除**：整条移除；git 可恢复，交付说明提一句

## Step 4：体检报告

固定带体检数字：机械项（索引水位、条目数、超长条目数、lint ERROR / WARN / INFO 计数）直接取
lint 输出；判断项（删除候选数、合并候选数）来自判断层与阶梯；候选清单逐条给依据

## Step 5：逐条确认执行

任何删除 / 合并 / 改写经用户点头才动文件；被否的条目不动。执行完复跑 lint 验证 ERROR 归零（用户明示保留的除外）
