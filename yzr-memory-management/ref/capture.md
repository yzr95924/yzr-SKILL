# 写入的执行细节

## MEMORY/ 在哪

MEMORY/ 只认当前目录一份：`./MEMORY/` 存在即用，不存在转初始化入口在当前目录建。不向上找父目录，不追 git root——前提是用户从项目目录启动 agent，当前目录即项目根，记忆的 @引用也按它解析

## 自主写入的检查

低质量条目多来自无人逐条检查的自主写入；以下检查全过才提：

1. **证据**：候选必须指向本轮具体事件（哪次纠正、哪个坑、用户哪句"以后都"）；没有证据的就是感想，不提
2. **负清单**：一律不收。能从代码 / git 推导的事实；AGENTS.md / 文档已写的（提议前 grep 验证）；操作步骤与任务经过；知识性结论（归 wiki）；某 skill 自身的用法与踩坑（改该 skill 源）；
   工具缺陷（报该工具）；跨项目偏好 / 本机专属（不进项目记忆，全局记忆放哪由用户自管）；可预见频繁更新的结论（版本 / 当前值 / 进行中状态）
   例外：临时方案可收，正文写适用版本
3. **作用域**：写得出约束对象（目录 / 文件 / 决策点）才提；写不出约束对象的不提
4. **合并优先**：先查索引，同主题已有条目则并入更新，禁止新增第二条

## 写到哪

- 一句话事实：短条目（行格式见 `assets/memory-index-template.md`）
- 需要展开为什么 / 边界：`<slug>.md` 条目（骨架见 `assets/memory-entry-template.md`）

写入顺序：**先写条目文件，再在索引挂其链接行**。中断只留孤儿条目（清理时能查到），不留死链（更糟）

## 确认与写入

- 用户点名的单条：合并、位置、格式判断照做，直接写入，判断依据写进交付说明
- 自主写入（批量沉淀、主动提议）：列表提议，每条标：内容一句话、位置、证据；用户确认后按序写入
- 宁缺毋滥：一轮提议 0~3 条，提 0 条也是正常结果
- 写前查索引用量：索引行数未达上限一半时免跑 lint 直接写入；接近上限才跑（以 lint 输出为准，命令见[章节](audit.md#lint-检查)）：
  报 `INDEX-BUDGET-HIGH` 时先给精简方案（合并摘要 / 短条目改写成文件条目 / 按 git 最后改动取最旧条目复查——排序只是选候选，判定仍走变更检查）再写入；
  报 `INDEX-BUDGET` 时转清理流程精简、回来再写
- 写入后交付说明提示：未 commit 前其他 worktree / 协作者看不到

## 批量沉淀（会话末）

触发："把这轮收获整理进记忆 / 沉淀一下"。按上述流程整批执行；任何一条被否不影响其余
