# 多模型评审编排

用户显式要求多模型 / 交叉评审才启用本文件；多模型只替换 Step 2 的发现生产，Step 3-6 机制不变，
呈现层的分组与来源标注由[章节](#合并)增补

**存在理由**：多评审员读同一份卷宗出发现，共识与分歧都能显式化；成本随票数线性涨，所以是显式 opt-in

## 默认名单

（用户指定，2026-10）：

- `yzr-dashscope/deepseek-v4.1-flash`
- `yzr-dashscope/glm-5.3`
- `yzr-dashscope/qwen3.8-flash`

## 名单闸门（本文件流程入口）

| 情形 | 处置 |
| --- | --- |
| 用户点名模型 | 点名覆盖默认；模糊名用 harness 的模型发现能力解析成精确 ID，一名多候选列出让用户挑、不静默代选；解析不到时如实报告并列现存相近候选，不拿替身凑数 |
| 未点名 | 直接用默认名单，不再确认往返（默认名单即预确认）；spawn 前在同一条消息里宣布名单与票数，有成本数据时随名单宣布成本，没有时以票数代成本 |
| spawn 前校验 | 逐个校验名单 ID 在本机可发现且 active；有失效时**停下报告**，列现存候选交用户裁定，不静默替换、不静默减票 |

## 编排

1. 物化：被审对象若是粘贴文字，先写成快照文件（系统临时目录下）；磁盘文件用原路径
2. 建卷宗：`python3 tools/build_review_packet.py --target <路径...> [--ref <路径...>]`（从 skill
   根运行；目录只收 `.md`，非 `.md` 文件须显式列路径才入卷宗）。卷宗 = BRIEF.md，只装会话数据（指纹清单 + 参照输入 + 共享扫描候选）由脚本生成；
   评审员角色与产物要求定义在[评审员模式](reviewer.md)，卷宗不复制 skill 内容
3. spawn：名单每个模型一个子代理，prompt 全同（单行：加载本 skill、按 ref/reviewer.md 以
   评审员模式执行、卷宗在 BRIEF 绝对路径），唯一差异是 harness 侧的 model 参数。**编排者不评审**：主 agent 上下文含主对话、与子代理
   不对称，亲自评审会击穿同一性保证；当前会话模型要入票须显式点名并同样走子代理
4. 并行 spawn；若 harness 不支持可指定 model 的子代理、或子代理无法加载本 skill，如实告知并退回单模型现状
5. 每个子代理审全文、不分段：跨段问题（前后重复、结构缺陷）是全文评审的固有意义；Step 1 的分段粒度只用于合并后的呈现批次

## 合并

收到 N 份输出后按序处置：

1. 核指纹：输出头部回显的 sha256 与卷宗清单不一致（含未回显）时，该份作废重跑，不进合并
2. 对比理解复述：某份核心主张明显跑偏时，该份降权并在结论标注，必要时重跑
3. 同位置（行号 ±2 内）、同规则名且语义指向同一问题的发现归并为一条，记来源模型集合；
   位置相邻但处置对象不同（如注水开头 vs 数据句复述）不并：机械套 ±2 会吞掉可执行信息；
   引用评审员原文作证据时逐字，不翻译、不转写
4. 分级呈现：共识（≥2 模型）独立成组排前，其后列单模型发现并标"仅 X 提出"；各组内按文档
   位置排序（与 Step 4"按位置顺序"的口径在此衔接）；映射不到 catalog
   规则名的发现由编排者尝试映射，映射不上按范围收敛原则过滤或标存疑，不进主表
5. 冲突（同一位置给出互斥处置，如一方判删、另一方判补或保留）单列"分歧"，不静默裁决；编排者给资深架构师倾向，最终交用户表态
6. 来源标注落在现有输出格式内（列口径见[报告模板](report-template.md)）：对话式在规则名后附 `【A+B】` / `【仅 X】`；报告形态写进问题列开头
7. 合并后的清单进 Step 3-6
