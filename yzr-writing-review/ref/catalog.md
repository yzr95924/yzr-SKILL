# 文档审查场景 Catalog（SSOT）

本文件是 yzr-writing-review skill 的核心知识资产 — 八组审查场景卡（第八组“指令文档”
按被审对象类型启用），细则自含，无第二层
规则文件。每条发现必须映射到至少 1 张卡片。

## 怎么读本 catalog

每张卡片 2 项列表：

- **信号**：看到什么模式应该想到这个场景
- **方案**：一两句话怎么改

卡片寻址用“组名.编号”（如 `Style.S2 拆超长句` 与 `Structure.S2 同义重述段`，纯编号
会撞车），正文引用一律带组前缀。示例与例外是判定标准的一部分：命中卡片后按示例比对，
命中例外条款则不算。
例外：第六组 AI 腔是指纹表形态（表格 + 判定点），不循 2 项卡片 schema——指纹管识别，
命中后引用对应规则卡处理。

## 第一组：Logic（逻辑）

### L1 逻辑矛盾

- **信号**：同一文档内两处说法直接打架，读者无法同时相信——结论与结论矛盾（§1 说
  "方案 A 最优"，§5 说"方案 B 最优"）；数据与结论方向相反（结论说"性能提升"，数据表
  显示下降）；定义前后不一（§2 定义 X 为 A，§4 用 X 指 B）
- **方案**：指出冲突两处位置 + 摘录原文，请作者裁定；**不替作者选**（那是意图变更）

### L2 论证链断裂

- **信号**：推理跳过必要环节——"因为并发高，所以要用 Kafka"中间缺"当前队列方案已到
  吞吐上限"；隐藏前提未声明（"我们选 monorepo"没讲"我们认同单仓编译提速"这个前提）；
  "如上所述"指到不存在的内容
- **方案**：补一句桥接（"当前 X 已到上限，所以……"）；隐藏前提显式化

### L3 结论与论据脱节

- **信号**：论据存在但支撑不了结论——以偏概全（单次实验推广到全场景）；反例未处理
  （论据清单里有不利项，结论无视它）；证据错位（用"开发效率"论证"运行性能"）
- **方案**：收窄结论到论据能支撑的范围，或补足以支撑的论据；两者都不行就删结论

### L4 无依据断言

- **信号**："最 / 第一 / 唯一 / 业界领先"无对比数据；"根据调研"但没给调研对象与规模；
  推测句（"应该可以 / 估计会"）写成陈述句（"可以 / 会"）
- **方案**：降级为明确判断（"我们认为"）+ 补依据，给不出就删；拿不准的标注
  "存疑请人工核对"，不验证（事实核查不属本 skill）

### L5 范围漂移

- **信号**：标题承诺"方案对比"，正文 80% 是背景介绍；开头说"只讨论 X"，后面整节讲 Y；
  附录级细节混入正文主干
- **方案**：对齐——改标题 / 删多余 / 移到附录；哪边是正主以用户意图为准，拿不准就问

### L6 主次颠倒

- **信号**：决定成败的论证一句话带过，实现细节占两页；对结论无关紧要的背景展开最长；
  读者看完记不住"这篇到底要说什么"
- **方案**：关键点展开到读者能带走结论；细节压缩 / 移附录；不改事实，只改分配

## 第二组：Structure（结构）

### S1 离题段

- **信号**：整段与主题无关（背景介绍跑偏 / 历史沿革注水 / 方法论自夸）
- **方案**：删段，或整体移到附录。判别：离题是相对于章节主题；标题 / 开头承诺的范围
  与正文不符 → 见 L5

### S2 同义重述段

- **信号**：整段换说法复述前文已讲过的观点，没有新信息（句级版本见 R1）
- **方案**：保留信息量大的那版，删另一版

### S3 章节职责交叉

- **信号**：两个章节讲同一件事 / 职责划分不清；同一信息分散在多个小节
- **方案**：合并章节，或明确"§A 讲定义、§B 讲用法"的分工

### S4 信息放置错位

- **信号**：前置条件放在后面讲；读者先看到结论后看到定义；跨章节阅读顺序断裂
- **方案**：移到正确位置，保证线性阅读顺序成立

### S5 层级碎片化

- **信号**：三级以下标题每节只有一句话；列表套列表；一段拆成多个"标题 + 一行"
- **方案**：合并层级，内容收拢回段落

## 第三组：Redundancy（冗余）

### R1 同义重述

- **信号**：同一个观点换一种说法再讲一遍（AI 最常见的注水手法）；"换句话说 / 也就是说 /
  in other words / that is to say"后面跟的如果不比前面多信息
- **方案**：保留信息量大的那版。前："这个方案风险很高。换句话说，采用这个方案可能让
  整个项目陷入不可控的境地。"后："这个方案风险很高，可能让整个项目失控。"；段落级
  版本见 Structure.S2

### R2 填充句

- **信号**：删掉后段落意思完全不变的句子——"这是一个非常重要的话题。" / "这个问题值得
  我们关注。" / "It is important to note that…"
- **方案**：删。判断法：把句子删掉读一遍——读者没损失，就是填充句

### R3 过度限定词

- **信号**：非常 / 极其 / 相当 / 十分 / 真的 / really / very / extremely / quite——
  削弱而非加强
- **方案**：默认删；只有限定词本身承载对比信息时保留（"极快"相对"快"是实测差异时）。
  前："这个方案非常有效。"后："这个方案有效。"（更好：给数据，"把延迟降到 50ms"）

### R4 注水开头结尾

- **信号**：开头"在当今……的时代 / 随着……的不断发展 / In today's fast-paced world"；
  结尾"总而言之 / 综上所述 / In conclusion"后跟全文复述
- **方案**：开头删，从正题起笔；结尾有行动项则改成一句行动号召（"下一步先跑基准
  测试"）

### R5 同义堆叠

- **信号**：两个及以上近义词并列当盾用——"帮助和协助" / "改进和优化" / "each and
  every" / "first and foremost" / "tips and tricks"
- **方案**：留一个（按语境选准的那个）

### R6 中文"的"链与"是……的"

- **信号**："的"连用 3 次以上；"是……的"强调结构非必要
- **方案**："系统的配置的管理的界面"→"系统配置管理界面"；"这个方案是可以落地的"→
  "这个方案可以落地"；空动词（"进行 / 做出 / 给予"）见 Style.S6

### R7 英文功能词冗余

- **信号**："in order to" / "due to the fact that" / "at this point in time" /
  "that"不消除歧义 / "There is / There are"开头
- **方案**："in order to"→"to"；"due to the fact that"→"because"；"at this point in
  time"→"now"；"I think that this works"→"I think this works"；"There are three
  options that we support"→"We support three options"

### R8 过度举例

- **信号**："例如 A、B、C、D、E、F"列一长串
- **方案**：保留 2–3 个最有代表性的。例外：清单本身是交付物（API 列表 / 错误码表）时
  不动

### R9 摘要与正文互注水

- **信号**：摘要段把正文每节复述一遍 + 正文里又有"本节将介绍……"预告
- **方案**：二选一——短文档（< 1500 字）删摘要 / 预告，正文自解释；长文档摘要只留
  "为什么 + 结论"，删细节复述

## 第四组：Style（风格）

### S1 句式长短错落

- **信号**：连续 5 句以上长度相近，节奏催眠
- **方案**：把其中一句砍成短句，制造停顿。前："系统首先接收请求，然后解析参数，接着
  校验权限，最后返回结果。"后："系统接收请求，解析参数，校验权限。最后返回结果。"

### S2 拆超长句

- **信号**：中文单句 > 60 字、英文单句 > 35 词，且无必要逻辑嵌套
- **方案**：拆。前："由于历史原因该模块在最初设计时没有考虑到后续业务量增长带来的
  并发压力，因此在高峰期经常出现响应缓慢甚至超时的情况，影响了用户体验。"后："该模块
  最初设计时没有考虑业务量增长带来的并发压力。高峰期因此经常响应缓慢甚至超时，影响
  用户体验。"

### S3 一段一意

- **信号**：一个段落里出现"另一方面 / additionally / 同时"开启新论点
- **方案**：拆段，一个段落只承载一个论点

### S4 主动语态优先

- **信号**：连续被动 / 无主语被动让动作的执行者消失——"请求被网关转发到后端服务"
- **方案**：改主动——"网关把请求转发到后端服务"。例外：执行者未知 / 不重要 / 刻意
  弱化（"数据被泄露"）时保留被动

### S5 具体优先于抽象

- **信号**：抽象名词 + 空动词替代可验证事实——"该方案在性能方面有一定的提升空间" /
  "We observed improvements in efficiency"
- **方案**：换成具体数据——"该方案 P99 延迟还能再降 20ms" / "Build time dropped from
  8 to 5 minutes"。原文没有具体数据时**不许编造**——改成泛指但具体的说法（"还能更快"
  而非"有一定提升空间"）

### S6 去名词化

- **信号**：中文"进行 / 实施 / 做一个 + 名词"、英文"make / perform / carry out +
  noun"
- **方案**：直接用动词——"进行一次部署"→"部署"；"做出决定"→"决定"；"make an
  adjustment"→"adjust"；"perform an analysis"→"analyze"

### S7 术语一致性

- **信号**：同一概念全文多个词——前面"工作区"，后面"workspace"，再后面"空间"
- **方案**：建立术语表（脑内即可）：概念 → 选定词，全文统一；中英混排时专有名词首次
  出现给中英对照（"工作区（workspace）"），之后固定一种；不许为了"避免重复"而换
  同义词——技术写作里换词 = 换概念

### S8 连接词节制

- **信号**："因此 / 然而 / 此外 / 而且 / 所以"每段开头都出现
- **方案**：能靠语序表达的逻辑关系就删连接词；一段最多保留一个。前："此外，系统还
  支持插件机制。然而，插件需要单独安装。因此，我们建议…"后："系统支持插件机制，但
  插件需要单独安装。我们建议…"

### S9 并列结构对齐

- **信号**：并列项语法结构不一致——名词 / 动宾 / 完整句混排
- **方案**：对齐。前："该工具支持格式化、代码检查，还能跑测试。"后："该工具支持
  格式化、代码检查和测试。"

### S10 易漂移引用

- **信号**：文档用**会随时间失效**的具体坐标做引用——代码 / 配置侧：行号（`src/foo.ts:712`）、
  commit 哈希、易变路径、具体版本号；文档侧：章节号引用（"见 §3.2"、"第 X 章"），章节一
  重排即失效；均未标注快照时间点。无坐标引用的纯散文不适用
- **方案**：代码 / 配置引用改用稳定符号名（函数 / 类 / 配置项）+ 文件路径；章节引用改用
  标题名 / 锚点链接；确需精确坐标时注明快照口径（"基于 commit abc1234"、"基于 2026-09 版
  章节结构"）。

## 第五组：Tone（语气）

### T1 正式度匹配文体

- **信号**：正式度与文体不符——技术文档里出现网络用语 / 感叹号连用 / emoji
- **方案**：先判文体，再定正式度基准，全文向基准收敛：

| 文体 | 基准 | 典型越界 |
| --- | --- | --- |
| 技术文档 / RFC | 冷静、陈述句、无感叹号 | "超好用！"、"nb" |
| wiki 笔记 | 半正式，允许第一人称思考痕迹 | 过度客套（"敬请指正"） |
| 邮件 / 汇报 | 礼貌但直接 | 开头三段寒暄不进正题 |
| 对外公告 | 正式、克制 | 网络用语、emoji |

### T2 去谄媚

- **信号**：对话式捧场开头（"Great question!" / "好问题！" / "这是一个非常好的想法"）；
  过度感谢与道歉（"非常感谢您的耐心等待"在非客服语境）；自我贬抑铺垫（"我才疏学浅，
  以下只是抛砖引玉"）
- **方案**：删，直接给内容。例外：邮件真实社交语境里的礼貌用语保留（那是写给真人看的）

### T3 去营销腔

- **信号**：技术内容里出现广告词——"业界领先 / 极致性能 / 完美解决 / revolutionary /
  cutting-edge / seamlessly"
- **方案**：换成可验证的说法："P99 延迟 50ms" / "兼容 99% 的现有配置"；感叹号在技术
  文档全文 ≤ 1 个。判别：事实性强宣称无依据（"业界领先"类）→ 见 L4；本卡只管修辞性
  广告词（seamlessly / revolutionary 类修饰腔）

### T4 人称一致

- **信号**：中文"你 / 您 / 我们 / 大家 / 咱们"随机轮换；英文 "you" 与 "we" 乱跳
- **方案**：全文统一——中文技术文档默认"你"；英文指南统一 "you"、团队决策记录统一
  "we"

### T5 中英语气差异

- **信号**：按字面对译另一种语言的语气
- **方案**：用目标语言的惯例——英文偏好直接祈使句开头（"Run the tests"），中文同场景
  更自然是陈述句（"先跑测试"）；中文的"请"高频出现会显得客服腔，技术文档里能省则省
  （"请参考"→"见"）；英文敬语（"Please kindly…"）在非正式文档里删掉不损失礼貌

### T6 对冲节制

- **信号**：hedging 连用——"可能在某种程度上或许"；一句 > 1 个对冲词
- **方案**：一句 ≤ 1 个、一段 ≤ 2 个；作者确有依据的不确定保留对冲并尽量写明依据
  （"可能——还没在生产验证过"）；对冲三连留一个

### T7 命令式与建议式的分寸

- **信号**：给读者指令用"你可能想要考虑运行 X"；表达作者主张用"我觉得也许 A 会好一点
  吧"
- **方案**：指令直接祈使句（"运行 X"）；主张陈述句 + 依据（"我们选 A，因为……"）；
  对上级 / 对外场景保留协商式语气（"建议……"），不改强硬

## 第六组：AI 腔（指纹表）

AI 生成文本的高频"指纹"。命中即按对应处理改写或删除。

### 中文指纹

| 指纹 | 处理 |
| --- | --- |
| "在当今快节奏的 / 瞬息万变的……时代 / 领域" 开头 | 见 R4 |
| "随着……的不断发展 / 日益普及" | 见 R4 |
| "值得注意的是 / 需要指出的是 / 众所周知" | 见 R2 |
| "不言而喻 / 毋庸置疑 / 显而易见" | 见 R2 |
| "让我们（一起）深入探讨 / 一探究竟" | 见 R4 |
| "不仅……而且……" 双重强调 | 拆成两句，或删"不仅而且" |
| "赋能 / 抓手 / 闭环 / 链路 / 颗粒度" 等黑话堆砌 | 换成具体说法；技术专有语境保留 |
| "总的来说 / 总而言之 / 综上所述" + 全文复述 | 见 R4 |
| "作为……，它……" 万能开头（"作为一个 AI 助手"） | 见 R4 |
| "的浪潮 / 的变革 / 的新篇章" 宏大叙事 | 换成具体事实 |
| "首先……其次……再次……最后……" 五段俱全 | 保留 ≤ 3 个，其余靠语序 |

### 英文指纹

| 指纹 | 处理 |
| --- | --- |
| "In today's fast-paced world" | 见 R4 |
| "It's worth noting that / It is important to note that" | 见 R2 |
| "delve into / embark on / navigate the landscape of" | 换成 dig into / start / handle 或直接动词 |
| "leverage / utilize" 滥用 | 换成 use（专有技术语境如 leverage a cache 保留） |
| "furthermore / moreover / additionally" 每段开头接力 | 见 Style.S8 |
| "not only … but also …" 每篇必现 | 拆句或删 |
| "In conclusion / To summarize" + 全文复述 | 见 R4 |
| "plays a (crucial/vital/pivotal) role in" | 换成具体作用："X handles Y" |
| "a testament to" / "a game-changer" / "the power of" | 删或换事实 |
| "Great question! / Certainly! / Absolutely!" 对话捧场 | 见 T2 |
| "seamlessly / effortlessly / robust" 副词三连 | 见 T3 |
| 过度 hedging："It's worth mentioning that it might potentially…" | 见 T6 |

### 结构指纹（中英通用）

- **三段式总结**：正文已经说清楚，结尾再来"综上所述 / In summary"复述 → 删
- **每段加粗小标题**：连续段落都以"**重点**：" / "**Key point:**"开头 → 保留真需要的，
  其余去粗体
- **排比成瘾**：连续三句以上同构排比（"它是……，它是……，它是……"）→ 保留一组，
  其余改正常句式
- **列表瘾**：一句话能说清的也拆成 bullet → 合并回句子；真清单保留
- **总分总强迫**：无论什么内容都"总起—分述—总结" → 短篇删总起和总结
- **假装对话**：非对话文体里插入"你可能会问……"自问自答 → 改陈述；FAQ 文体保留

### 标点与排版指纹

- **破折号"——"/ em-dash**：默认一律换常规标点（插入语改括号或逗号，并列补述改冒号
  或另起句号）；豁免收窄到引文与真正的修辞停顿。中文 AI 腔最高频指纹之一，单点命中
  即处理、不等密度阈值
- **CJK 角引号"「」/『』"**：中文技术文档正文用弯双引号""，混入「」属风格漂移；
  『』同理。单点命中 → 改""，豁免引文与其他语言原文语境
- **emoji 点缀**：技术文档 / 正式文档里段落开头 emoji（🚀💡✨）→ 删；用户原文自带且
  文体允许（个人笔记）保留
- **加粗成瘾**：每段都有加粗短语 → 只保留真正需要扫读定位的（术语定义 / 警告）
- **"首先 / 其次 / 最后"序号词** 与编号列表同时出现 → 删序号词

### 判定点

- 单个指纹出现 ≠ AI 生成，人也会写"值得注意的是"——**命中 ≥ 3 类指纹**才按"去 AI 腔"
  处理；单点命中按对应维度的规则（Redundancy / Style / Tone）正常处理
- 黑名单是删改依据，不是禁用词表：语境需要时（引文 / 反讽 / 专有名词）保留
- 处理目标不是"检测不出来"，是"读着像作者自己写的"——别为了规避检测引入怪句

## 第七组：跨文档 SSOT（仅参照输入存在时启用）

### X1 口径漂移

- **信号**：同一概念在两处文档定义不同 / 术语用法不一致（一处"工作区"一处
  "workspace"）
- **方案**：统一到参照输入的 SSOT 版本，另一处改引用

### X2 内容重复

- **信号**：本文与参照文档逐字 / 逐段重复（权限说明、配置步骤等维护双份的内容）
- **方案**：删重复段，改为指向 SSOT 的引用

### X3 事实冲突

- **信号**：本文数据 / 结论与参照文档矛盾（版本号、时间、性能数据不一致）
- **方案**：指出冲突双方位置，请作者裁定谁为准，改另一处

### X4 上下文重复定义

- **信号**：已在 SSOT 定义过的概念在本文又展开重述
- **方案**：一句话引用 + 链接即可，不重写定义

## 第八组：指令文档（Instr——被审对象是给 agent 执行的指令时启用）

适用对象：SKILL.md / AGENTS.md / system prompt / rules 文件 / CLI 工具说明——读者是执行中
的 agent 而非人。**不是第八个维度**：卡片仍是上文维度的场景特化，只是判据换成 agent 读者
版——冗余从"读者有损失吗"变成"**删掉这句，称职 agent 会做错吗？不会 → 删**"。

### I1 agent 通识复述

- **信号**：把 agent 本就会的操作逐步铺开（"打开文件 → 解析 → 写入"）；复述通识概念
  （解释什么是 PDF / JSON）；一行命令或代码能替代的写成整段散文
- **方案**：删，或替换为一行命令 / 代码示例；只保留 agent 不可能知道的东西（私有格式、
  环境怪癖、踩过的坑）；成片出现按 Structure.S2 判

### I2 疤痕组织

- **信号**：为单次历史失败在正文打补丁（"别忘了 X"式防御句）；预先回应假想读者的误读
  （"这不是说 Y"）；一条规则配多段原因论证
- **方案**：删——没来自实际观察到的失败的补丁 = 无依据；确有护栏必要就改写成正面规则一句

### I3 禁令无 why

- **信号**：NEVER / ALWAYS / 严禁全大写堆叠且无理由句；只写"不许做什么"，不写"为什么会
  出错"
- **方案**：补"为什么"——agent 依理由而非词强遵从，有理由才能外推到未覆盖场景；补不出
  理由的禁令大概率本就该删（常与 I2 同现）

### I4 时间性信息内联

- **信号**："自 v2 起删除了 X" / "旧版做法是…现在改为…"等自身演进史写进规范正文——读者
  （agent）会把旧行为描述误判为"仍是可选路径"
- **方案**：演进叙事移 git commit / CHANGELOG，正文最多留一句路标。**例外**：对外部依赖的
  版本**约束**（"Python ≥ 3.7"）是当前状态要求，照写

### I5 决策点 N 等价选项

- **信号**：某一步列 ≥ 3 个等价选项不给推荐（"可用 A / B / C / D…"）——把选择责任推给
  读者，执行 agent 反而拖慢决策
- **方案**：1 个推荐 + 1 个 escape hatch；其余选项收进"何时才选它"的一句限定

### I6 示例堆叠

- **信号**：同一要点配多个平庸样例（模板填空 × N、同一示例多语言各写一遍）。与 R8 分工：
  R8 管内联列举（"例如 A、B、C…"），本卡管块级示例
- **方案**：留一个最相关的完整可运行示例，其余删——agent 会自己移植语言 / 改场景

### 本组三条判定注

- **同 skill 内重抄**：同一规则在 SKILL.md 与 ref/ 多处展开 → 按 X2 判，删重处留
  指针（对 skill 文件集做大范围体检时，该文件集自身就是参照输入）
- **跨体裁双写**：同一信息以图 / 表 / 散文 / 列表各承载一遍——字面不重叠、grep 抓不到
  → 按 S2 判，语义归并只留一份
- **description 常驻（SKILL 类文档特轴）**：frontmatter description 等价于一直加载，正文
  复述其 selection 层内容（触发语 / "何时调、何时不调"类路由结论）→ 按 X2 同文档双写判、
  删正文侧；审 SKILL.md 必须把 frontmatter 纳入比对视野。豁免：权限 / 纪律句在**执行点**
  的重述——常驻 ≠ 执行时刻被注意，归通用删除测试判
