---
name: yzr-skill-management
description: |
  创建、改进或审计 agent skill，并维护 skill 骨架标准。
  当用户提到做 / 沉淀 skill、重做某个 skill、改 skill 或其触发描述、审计 skill、
  改骨架标准 / 模板时使用。
  不适用：skill 机制答疑、调试 skill 的脚本代码、删除 / 发布 / 批量迁移 skill、
  不涉及 skill 的普通代码或文档工作。
---

## 输入与输出

- **输入**：用户诉求与目标 skill 目录（创建可无目标；标准维护的目标是模板与本文件）
- **输出**：审计只交付报告、不改文件；创建 / 改进交付 skill 改动。细则见[章节](#工作流)对应小节

## 执行原则

- **单一来源**：同一条规则或事实只写在一处：形状归模板，可机械判定的检查归脚本
  （脚本从模板读取，不内嵌定义副本），其余内容默认归 SKILL.md，命中门槛时下放 ref/
  （见"子目录按门槛建"）；其余位置只引用，不转述。
- **引用用稳定标识**：交叉引用用名称或链接，不用序号、行号——序号在条目增删后仍指向第 N 项，
  内容却已不同，且不报错；名称变更则全库检索立刻暴露。跨节引用写 `[章节](#节名)`：节名只进锚点
  一次，链接文字固定、可机械检查；粗体条目无锚点，引用用名称。
- **删行测试**：description 每会话注入、正文每激活加载、ref 用到才读，冗余文字持续占用上下文。
  对每一行问：删掉它，称职的 agent 会做错事吗？不会则删；门禁全绿只证形式合规。
- **新增须举证**：目录、工具、字段、规则默认不建；建前答两问——命中哪条门槛（见"子目录按门槛建"）、
  实录证据是什么（见"实证优先"），任一答不出则不建。
- **实证优先**：新增规则须给出任一实录证据：已发生的事故、测试或裸跑记录、用户反馈。
  无实录的判断标注"暂定"，裸跑或定性测试后复核。
- **对照开放规范**：新立内容标准先查 Agent Skills 开放规范。与规范一致的，不必另行记录；
  严于规范的，记录加严理由和放宽条件。
- **节内容边界**：每节只写节名所指的内容：`输入与输出` 只写无法从 description 推断的前置与交付
  （没有则一行收口）；`执行原则` 只写跨入口通用的判断规则；`工作流` 只写操作步骤，
  多入口的分流判据放第一个小节。触发时机只写在 description。
- **description 写法**：三行句式见模板槽位。每个关键词对应一类用户会真实发出的请求，
  不用整句引号例句；每个负例对应一类实际容易误触发的请求。
- **子目录按门槛建**：ref/ = 执行细节超过一屏，或被多处阅读；tools/ = 存在可机械判定通过与否的
  重复操作（冒烟测试放 tools/tests/）；assets/ = 有可拷贝的模板或静态资源；eval/ = 要跑定性测试。

## 工作流

做新 skill → 创建；改现有 skill（含本 skill 的模板与执行原则）→ 改进；检查 skill 是否符合标准 → 审计。

### 创建

1. **访谈定范围**：当前对话可能已含要沉淀的工作流——先从对话历史抽取（用到的工具、步骤顺序、
   用户做过的修正、输入输出格式），再补缺口。问清并记录每个答案落进哪一节：让 agent 能做什么、
   用户会说什么话触发 → description 关键词；期望交付什么 → `输入与输出`；不管什么、与相邻 skill
   怎么分工 → description 不适用行；流程中哪些步骤是机械的（零判断、可枚举）→ tools/ 候选。
   范围与候选清单交用户确认，确认前不写正文。
2. **裸跑取证**（发起前问用户，subagent 有成本）：不带 skill 实跑 2–3 个典型 prompt，
   逐字记录 agent 漏做了什么、以及它的借口（原样摘抄，不预写假想借口）。按失败类型定规则形式：
   知道但找借口绕开 → 禁令句，把实录借口写进禁令；想做但不会 → 配方式步骤；不知道 / 引错地方 →
   参考资料。裸跑记录是正文规则的实证来源。
3. **生成骨架、逐段起草**：跑 `tools/skeleton.py new <name>` 生成骨架。frontmatter 按模板槽位填，
   description 按"description 写法"；正文按"节内容边界"填写，**每写一段就与用户确认一段**：
   一段 = 一节或节内若干条，确认后再继续下一段；不要一次产出大段内容再交用户整体 review——
   review 成本高，问题成堆后只能返工。第 1 步的机械候选此时逐条定夺：先按"新增须举证"过一遍，再算代价账——
   context 节省 × 使用频率，是否高于脚本行数 + 冒烟维护成本；一行 shell 能做完的、一年跑不了几次的不做脚本，
   留 md 的记一句理由。
4. **定性测试**（发起前问用户，subagent 有成本）：用例 prompt 用用户真实会说的话，从裸跑的 2–3 条
   起步，先交用户确认再跑；每条带客观可核验的期望，写入 `eval/evals.json`。subagent 实跑，
   对照期望逐条判断，按结果修改正文并重跑，直到通过且用户满意；收敛后补相邻负例扩集，防过拟合。
5. **收口**：`check` 全绿；目标仓库有 lint / format 门禁的一并跑；有 tools/ 时跑其冒烟；交用户过目。

### 改进

1. 通读目标 skill，定位改动涉及的节，按"节内容边界"归位新内容。
2. 新增规则按"实证优先"给出实录；改 description 时按"description 写法"复核关键词与真实请求的对应。
3. 有效性验证（行为性改动；发起前问用户，subagent 有成本）：用实录里的原失败场景重跑，
   不得再那样失败；有 `eval/evals.json` 的一并跑回归，复现用例追加进去；改 description 的跑触发正负例。
   单点编辑豁免。
4. 改动对象是本 skill 的模板或执行原则时：先经用户确认，模板与正文同批改完。
5. 收口同创建；一批改动触及多节 / 多文件时，交付前提议对目标 skill 全文审计（用户点头才执行），单点编辑豁免。

### 审计

1. 机械趟先行：跑 `tools/skeleton.py check <skill-dir>`；目标 skill 有 tools/ 时加跑冒烟，失败一并列入报告。
2. 精读 skill 目录全部文件，对照[章节](#执行原则)逐条给结论，每条附文件与原文引用为证据；只报告，不修改。
3. 报告每条有处置与去向，未处置不得收工：违反项附修法建议，修复经用户点头后走改进；"删行测试"不过的
   列入待删候选；纯文字质量转 yzr-writing-review，tools/ 代码与脚本转 yzr-coding-review。
