---
name: yzr-skill-management
description: |
  创建、改进或审计 agent skill，并维护 skill 骨架标准。
  当用户提到做 / 沉淀 skill、重做某个 skill、改 skill 或其触发描述、审计 skill、
  改骨架标准 / 模板时使用。
  不适用：skill 机制答疑、调试 skill 的脚本代码、删除 / 发布 / 批量迁移 skill、
  不涉及 skill 的普通代码或文档工作。
---

## 输入与输出

- **输入**：用户诉求与目标 skill 目录（创建可无目标；标准维护的目标是模板与本文件）
- **输出**：审计只交付报告、不改文件；创建 / 改进交付 skill 改动

## 执行原则

### 设计原则

- **单一来源**：同一条规则或事实只写在一处：形状归模板，能自动判定的检查归脚本
  （脚本从模板读取，不内嵌定义副本）；其余内容默认归 SKILL.md，多到值得拆时进 ref/（见"目录按需建"）；其余位置只引用，不转述
- **机械活脚本化**：能自动判对错的检查、零判断可枚举的重复动作（生成骨架、批量转换这类），
  都写成脚本。不靠正文提醒，也不让 agent 每次亲手重做，亲手做一百次就有一百种结果。
  不合算的不做：误报太多或比规则还重的检查不立；一行 shell 能做完、一年跑不了几次的动作
  不写成脚本
- **执行路径从简**：设计工作流时数一遍 agent 照做要几次工具调用、读几个文件；能一次调用做完的
  不拆成多步，能一次读完的不让读两次，能并行发起的不串行
- **先文字后脚本**：结构与表达上的需要，先用正文、模板、小节这些文字办法解决；
  文字办法确实不够用了，再动脚本和检查器
- **脚本黑盒化**：agent 调用脚本不读源码，对外契约全写在 `--help` 里（参数、输入形状、退出码）
- **目录按需建**：ref/ = 执行细节超过一屏，或几个地方都要读；tools/ = 有值得写成脚本的检查或重复动作
  （冒烟测试放 tools/tests/）；assets/ = 有可拷贝的模板或静态资源；eval/ = 要跑定性测试。
  这些目录只放按场景才读的内容，每次激活都要读的留在正文
- **依赖不成环**：skill 之间依赖单向，A 依赖 B，B 就不能再依赖 A（隔着第三个 skill 绕一圈也算）。
  判断标准：离开对方，这个 skill 的活还能不能干完。能干完就只是顺带提一句名字，不算依赖。
  靠语义判断，不做自动检查
- **不替用户设计**：素材（对话 / 旧目录 / 裸跑记录）和用户确认都没覆盖的细节，不自行补齐默认值；
  素材没回答的决策点列成开放问题，交用户定。写进正文的每条规则都要答得出出处：哪次对话、
  哪条裸跑记录、哪句原话；答不出的不写

### 写作原则

- **删行测试**：description 每次会话注入、正文每次激活都整篇加载，文字效率要求高。
  对每一行问：删掉它，称职的 agent 会做错事吗？不会就删。规则的"为什么"只在改变
  边界行为时留在正文，其余归档进 commit。门禁全绿只证形式合规
- **不写演进史**：修改日期、改动原因、新旧对比这类演进史归 commit；正文只写当前生效的规则与事实
- **直陈**：陈述句直写，不起绰号、不造小标题式的新词；给一个东西起名，只为别处需要按名提到它
- **标点从简**：条目句末不加句号；全角标点照常，全角符号不用（★、▶、→ 这类图形 / 装饰符号），
  转折、承接这类关系用文字写；句中标点只在帮着断结构时用；引文、代码与模板槽位不动
- **排版不渲染**：读者是 agent，读原文不读渲染结果；表格、mermaid、ASCII 图这类排版语法不写
- **节内容边界**：每节只写节名所指的内容：`输入与输出` 只写无法从 description 推断的前置与交付
  （没有则一行收口）；`执行原则` 只写跨入口通用的判断规则，条目多了再分设计 / 写作两小节；
  `工作流` 只写操作步骤，多入口的分流判据放工作流节首。触发时机只写在 description
- **引用不用序号**：交叉引用用名称或链接，不用序号、行号。跨节引用写 `[章节](#节名)`；粗体条目
  没有锚点，引用就写它的名字。提到别的 skill 只写对方的名字，不指它内部的节名 / 路径。
  同一个概念从头到尾一个叫法
- **description 写法**：只服务触发判定，三行句式见模板槽位。每个关键词对应一类用户真会发出的请求，
  不用整句引号例句；每个负例对应一类真容易误触发的请求；漏触发代价高的补主动声明；步骤串讲不写
- **agent 中立**：正文与 description 默认泛指执行环境；点名具体 agent 或其特有机制时，就地讲清为什么

## 工作流

做新 skill 走创建，步骤见 `ref/create.md`；整体重写现有 skill 的正文（重做）走创建，各步的重做场景条款适用；
改现有 skill（含本 skill 的模板与设计原则 / 写作原则）走改进；检查 skill 是否符合标准走审计。
创建与改进的最后一步相同：`check` 全绿；目标仓库有 lint / format 门禁的一并跑；有 tools/ 时跑其冒烟；交用户过目

### 改进

1. 通读目标 skill，定位改动涉及的节，按"节内容边界"归位新内容；改动面是整个 skill 目录
   （frontmatter / 正文 / ref / tools / eval 联动）
2. 改 description 时按"description 写法"复核关键词与真实请求的对应；
   被质疑某句时，先按"删行测试"试试能不能直接删，删不掉才改写，不靠加解释的话回应质疑
3. 有效性验证（行为性改动）：用触发本次改动的失败场景重跑，
   不得再那样失败；有 `eval/evals.json` 的一并跑回归，复现用例追加进去；改 description 的跑触发正负例，
   方法见 `ref/qualitative-loop.md`。单点编辑豁免
4. 改动对象是本 skill 的模板或设计原则 / 写作原则时：先经用户确认，模板与正文同批改完；
   改完全仓跑一遍 check，过不了的老 skill 列成清单交用户定处置
5. 一批改动触及多节 / 多文件时，交付前提议对目标 skill 全文审计（用户点头才执行），单点编辑豁免

### 审计

1. 跑 `python3 yzr-skill-management/tools/skeleton.py check <skill-dir>`；目标 skill 有 tools/ 时加跑冒烟，失败一并列入报告
2. 精读 skill 目录全部文件，结构项对照[章节](#设计原则)、文字项对照[章节](#写作原则)逐条给结论，每条附文件与原文引用为证据
3. 报告每条有处置与去向，未处置不得收工：违反项附改法建议，修复经用户点头后走改进；"删行测试"不过的
   列入待删候选；纯文字质量转 yzr-writing-review，tools/ 代码与脚本转 yzr-coding-review
