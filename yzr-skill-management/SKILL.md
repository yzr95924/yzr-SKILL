---
name: yzr-skill-management
description: |
  创建、改进或审计 agent skill，并维护 skill 骨架标准。
  当用户提到做 / 沉淀 skill、重做某个 skill、改 skill 或其触发描述、审计 skill、
  改骨架标准 / 模板时使用。
  不适用：skill 机制答疑、调试 skill 的脚本代码、删除 / 发布 / 批量迁移 skill、
  不涉及 skill 的普通代码或文档工作。
---

## 输入与输出

- **输入**：用户诉求与目标 skill 目录（创建可无目标；标准维护的目标是模板与本文件）
- **输出**：审计只交付报告、不改文件；创建 / 改进交付 skill 改动。细则见[章节](#工作流)对应小节

## 执行原则

### 设计原则

- **单一来源**：同一条规则或事实只写在一处：形状归模板，可机械判定的检查归脚本
  （脚本从模板读取，不内嵌定义副本），脚本的参数与用法以 `--help` 自描述为准、正文不重抄；
  其余内容默认归 SKILL.md，命中门槛时下放 ref/（见"子目录按门槛建"）；其余位置只引用，不转述
- **机械化优先**：可机械判定的规则尽量落成脚本检查，不靠正文提醒
  误报频繁或实现比规则本身更重的检查不立，先修判据再立
- **机械层最后动**：结构与表达需求先用正文、模板、嵌套小节等文本手段达成；文本手段穷尽后才改
  脚本与检查器
- **脚本自述备查**：脚本的 docstring 写契约点与备查决策（加严理由、放宽路径），不写复述代码的注释；
  正文不另抄
- **子目录按门槛建**：ref/ = 执行细节超过一屏，或被多处阅读；tools/ = 存在可机械判定通过与否的
  重复操作（冒烟测试放 tools/tests/）；assets/ = 有可拷贝的模板或静态资源；eval/ = 要跑定性测试
  门槛只管按场景才读的内容，每次激活都读的常驻内容不拆进 ref/
- **依赖不成环**：skill 间依赖单向，A 依赖 B 时 B 不得再依赖 A（含经由第三个 skill 的间接环）
  判据：没有对方，本 skill 的工作流能否走完——能走完是转交指称，不受此限。依赖判断靠语义，
  不立机械检查

### 写作原则

- **删行测试**：对每一行问：删掉它，称职的 agent 会做错事吗？不会则删。规则的"为什么"只在改变
  边界行为时留在正文，其余归档进 commit。门禁全绿只证形式合规
- **直陈**：陈述句直写，不造昵称与小标题式名称；名字只在别处按名指称它时存在
- **标点从简**：条目句末不加句号；不用输入法直接打不出的符号（如 →），映射与路由用文字表达；
  句中标点只在承载结构时用；引文、代码与模板槽位不动
- **节内容边界**：每节只写节名所指的内容：`输入与输出` 只写无法从 description 推断的前置与交付
  （没有则一行收口）；`执行原则` 只写跨入口通用的判断规则，内部分设计 / 写作两小节；
  `工作流` 只写操作步骤，多入口的分流判据放工作流节首。触发时机只写在 description
- **引用用稳定标识**：交叉引用用名称或链接，不用序号、行号。跨节引用写 `[章节](#节名)`；粗体条目
  无锚点，引用用名称。提及其他 skill 只写对方 skill 名，不指其内部节名 / 路径。同一概念全程同一名称
- **description 写法**：三行句式见模板槽位。每个关键词对应一类用户会真实发出的请求，
  不用整句引号例句；每个负例对应一类实际容易误触发的请求
- **agent 中立**：正文与 description 默认泛指执行环境；点名具体 agent 或其特有机制时，就地讲清为什么

## 工作流

做新 skill 走创建；整体重写现有 skill 的正文（重做）走创建，各步的重做场景条款适用；
改现有 skill（含本 skill 的模板与设计原则 / 写作原则）走改进；检查 skill 是否符合标准走审计。

### 创建

1. 素材两来源——当前对话（抽用到的工具、步骤顺序、用户做过的修正、输入输出格式），
   或被重做的旧 skill 目录（旧正文作反面参照、tools / assets 是已验证资产、旧 evals 是用例素材；
   旧执行原则逐条给处置——以原文逐条核对，不凭摘要与记忆；吸收 / 改写 / 弃用，弃用须给理由）；
   先抽取再补缺口。问清并记录每个答案落进哪一节：让 agent 能做什么、
   用户会说什么话触发归 description 关键词；期望交付什么归 `输入与输出`；不管什么、与相邻 skill
   怎么分工归 description 不适用行；流程中哪些步骤是机械的（零判断、可枚举）归 tools/ 候选
   范围与候选清单交用户确认，确认前不写正文
2. 裸跑（发起前问用户，subagent 有成本）：不带 skill 实跑 2-3 个典型 prompt，
   逐字记录 agent 漏做了什么、以及它的借口（原样摘抄，不预写假想借口）。重做场景先对同一素材
   实跑一次现有工具作对照基线，裸跑记录与其对比差值。按失败类型定规则形式：
   知道但找借口绕开归禁令句，把裸跑借口写进禁令；想做但不会归配方式步骤；能力有但不知道
   已有工具归统一入口禁令（否则自建等效路径，产物发散、代价失控）；
   不知道 / 引错地方归参考资料。裸跑记录是正文规则的实证来源
3. 跑 `tools/skeleton.py new <name>` 生成骨架；重做场景跳过 new（目录已存在），
   原位替换正文，tools / assets 沿用为默认。frontmatter 按模板槽位填，
   description 按"description 写法"；正文按"节内容边界"填写，**每写一段就与用户确认一段**
   （一段 = 一节或节内若干条；用户显式授权可豁免：分段写完一次性整体交审，返工与取证记录照记）
   第 1 步的机械候选此时逐条定夺：先算代价账——
   context 节省乘使用频率，是否高于脚本行数 + 冒烟维护成本；一行 shell 能做完的、一年跑不了几次的不做脚本，
   留 md 的记一句理由
4. 定性测试（发起前问用户，subagent 有成本）：先读 `ref/qualitative-loop.md`（裸跑、行为、
   触发三套指令模板与工作区、evals 格式）。用例 prompt 用用户真实会说的话，从裸跑的 2-3 条
   起步，先交用户确认再跑；每条带客观可核验的期望，写入 `eval/evals.json`。subagent 实跑——
   行为测试按协议以正文内联法执行（harness 加载的是安装快照非仓库新文）；description 草案以触发
   正负例判激活面；对照期望逐条判断，按结果修改正文并重跑，直到通过且用户满意；
   收敛后补相邻负例扩集，防过拟合
5. **收口**：`check` 全绿；目标仓库有 lint / format 门禁的一并跑；有 tools/ 时跑其冒烟；交用户过目

### 改进

1. 通读目标 skill，定位改动涉及的节，按"节内容边界"归位新内容；改动面是整个 skill 目录
   （frontmatter / 正文 / ref / tools / eval 联动），不只 SKILL.md
2. 改 description 时按"description 写法"复核关键词与真实请求的对应；
   被质疑某句必要时，先按"删行测试"验证能否删，删不掉才改写——不以追加解释回应质疑
3. 有效性验证（行为性改动；发起前问用户，subagent 有成本）：用触发本次改动的失败场景重跑，
   不得再那样失败；有 `eval/evals.json` 的一并跑回归，复现用例追加进去；改 description 的跑触发正负例，
   方法见 `ref/qualitative-loop.md`。单点编辑豁免
4. 改动对象是本 skill 的模板或设计原则 / 写作原则时：先经用户确认，模板与正文同批改完
5. 收口同创建；一批改动触及多节 / 多文件时，交付前提议对目标 skill 全文审计（用户点头才执行），单点编辑豁免

### 审计

1. 跑 `tools/skeleton.py check <skill-dir>`；目标 skill 有 tools/ 时加跑冒烟，失败一并列入报告
2. 精读 skill 目录全部文件，结构项对照[章节](#设计原则)、文字项对照[章节](#写作原则)逐条给结论，每条附文件与原文引用为证据；只报告，不修改
3. 报告每条有处置与去向，未处置不得收工：违反项附修法建议，修复经用户点头后走改进；"删行测试"不过的
   列入待删候选；纯文字质量转 yzr-writing-review，tools/ 代码与脚本转 yzr-coding-review
