# yzr-polish-writing

把一段已存在的文字改写得更好读：去 AI 腔、砍冗余、顺风格、调语气。**改写，不是诊断报告**。

## 何时使用

- 用户显式说"润色 / 改写 / 精简 / 去 AI 味 / polish / rewrite / make it less verbose"
- 用户抱怨"这段读起来一股 AI 味 / 太啰嗦 / 语气不对"，要的是改好的版本
- agent 刚产出一大段 prose（设计文档正文 / wiki 页面 / 邮件草稿），用户要求再过一遍

## 何时不使用

- 翻译（中↔英语言转换）→ 不是润色，直接做
- 事实核查 / 数据校对 → 本 skill 保事实，不验证事实
- 改代码 / 代码注释重写 → 走代码工具
- 内容意图变更（"帮我加个观点" / "这段结论不对，重写"）→ 是创作不是润色
- 从零写文档 → 是创作不是润色（写完再润色才走本 skill）
- 单步问询（"这句话什么意思"）→ 直接答

## 输入 / 输出

**输入**（任一形态）：

- 直接粘贴的文本片段
- 本地文件路径（agent 自己读；改写后**就地编辑**该文件）
- 对话中 agent 刚产出的一段 prose

**输出**：

1. 改写后的完整版本（文件输入 → 就地编辑；粘贴输入 → 对话内输出全文）
2. 简短改动说明：按维度列点（风格 / 冗余 / 语气 / AI 腔各改了什么），每条一行，
   不长篇解释——用户要的是结果，不是论文

## 执行原则 / 边界

1. **保语义保事实**：不增删观点、不引入原文没有的信息、不改数据 / 结论 / 引用；
   拿不准的事实表述原样保留，改动说明里标注"此处存疑请人工核对"
2. **最小改动**：只改有规则依据的地方；规则没覆盖的个人文风（口头禅、习惯句式）保留，
   polish 不是 ghostwrite——改完应该还像原作者写的，只是更干净
3. **规则 SSOT**：四类规则的唯一真源在 `references/{style,redundancy,tone,ai-tells}.md`，
   本文件不重抄；每条改动可追溯到至少一条规则
4. **结构不动**：Markdown 标题层级、代码块、frontmatter、链接、图片引用、表格结构、
   列表嵌套全部原样保留；只改正文 prose（句子级）
5. **中英分流**：先判语言再选规则——中文规则不治英文病；中英混合文档逐段判语言
6. **直接改写**：默认给改好的版本，不是问题清单；用户要诊断报告时会显式说"先别改，告诉我哪有问题"

## 工作流 / 步骤

### Step 1: 收集文本 + 判定语境

解析输入（粘贴 / 路径 / 对话内文本），判定：

- **语言**：中文 / 英文 / 中英混合（混合则逐段判）
- **文体**：技术文档 / wiki 笔记 / 通用 prose（影响 tone 规则的正式度基准）
- **篇幅**：> 2000 字时按章节 / 小节分批改写，避免一次性重写丢掉结构

### Step 2: 诊断问题维度

先通读一遍，对照 `references/ai-tells.md`（AI 腔黑名单）+ `references/redundancy.md`
（冗余信号）扫一遍，定位这段文字主要病在哪几个维度——**只加载有问题的维度对应的
规则文件**，四个文件不全部预读。

### Step 3: 加载规则

按诊断结果 Read 对应 `references/*.md`：

- 句子拗口 / 节奏差 / 术语乱跳 → `references/style.md`
- 啰嗦 / 注水 / 重复观点 → `references/redundancy.md`
- 语气不对（太谄媚 / 太生硬 / 太营销） → `references/tone.md`
- 一股 AI 味 → `references/ai-tells.md`

### Step 4: 改写

逐规则改写。遵守「执行原则 / 边界」：保语义、最小改动、结构不动。
拿不准该不该改的地方——不改，在改动说明里提一句。

### Step 5: 自检 + 输出

输出前自检 3 问：

1. 有没有改掉原文的事实 / 观点 / 数据？（应无）
2. 有没有引入原文没有的新信息？（应无）
3. 每处改动能否指到至少一条规则？（应能）

然后给：改写版 + 简短改动说明（按维度列点，每条一行）。

## 参考样例

**输入**（典型 AI 腔中文）：

> 在当今快节奏的软件开发领域，代码质量的重要性不言而喻。值得注意的是，
> 代码审查不仅能够帮助我们发现潜在的缺陷，而且还能够促进团队成员之间的知识共享。
> 总而言之，让我们深入探讨一下代码审查的最佳实践。

**改写后**：

> 代码审查有两个直接收益：发现缺陷，以及让团队成员互相了解彼此的代码。
> 下面是几个实践中验证过的做法。

**改动说明**：

- AI 腔：删"在当今快节奏…不言而喻"模板开头、"值得注意的是"、"总而言之，让我们深入探讨"
- 冗余："不仅能够…而且还能够"双重注水压缩为一句
- 风格：抽象名词堆叠（"知识共享的促进"）改成具体说法

## 与相邻 skill 的关系

- 不改写后要发去 Outline Wiki 的编排——发布走 `yzr-outline-wiki`，本 skill 只管文字本身
- 不改写后要沉淀进本地 wiki 的组织决策——走 `yzr-llm-wiki-management`
- 规则库本身要迭代（"把这条偏好加进规则"）→ 直接编辑对应 `references/*.md` 文件
