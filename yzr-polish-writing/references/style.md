# 写作风格规则（style）

句子层面的"怎么写才顺"。适用：句子拗口、节奏单调、术语乱跳、抽象名词堆叠。
每条规则给出中英对照示例；只改命中的规则，不全文重写。

## S1 句式长短错落

连续 5 句以上长度相近 → 节奏催眠。把其中一句砍成短句，制造停顿。

- 前：系统首先接收请求，然后解析参数，接着校验权限，最后返回结果。
- 后：系统接收请求，解析参数，校验权限。最后返回结果。

## S2 拆超长句

中文单句 > 60 字、英文单句 > 35 词，且无必要逻辑嵌套 → 拆。

- 前：由于历史原因该模块在最初设计时没有考虑到后续业务量增长带来的并发压力，
  因此在高峰期经常出现响应缓慢甚至超时的情况，影响了用户体验。
- 后：该模块最初设计时没有考虑业务量增长带来的并发压力。高峰期因此经常
  响应缓慢甚至超时，影响用户体验。

## S3 一段一意

一个段落只承载一个论点。段落里出现"另一方面 / additionally / 同时"开启新论点 → 拆段。

## S4 主动语态优先

被动不是错，但连续被动 / 无主语被动让动作的执行者消失 → 改主动。

- 前：请求被网关转发到后端服务。（谁在配置网关？语境清晰时）→ 后：网关把请求转发到后端服务。
- 前：The configuration is loaded by the framework. → 后：The framework loads the configuration.
- 例外：执行者未知 / 不重要 / 刻意弱化（"数据被泄露"）时保留被动。

## S5 具体优先于抽象

抽象名词 + 空动词 → 具体名词 + 实动词。

- 前：该方案在性能方面有一定的提升空间。→ 后：该方案 P99 延迟还能再降 20ms。
- 前：We observed improvements in efficiency. → 后：Build time dropped from 8 to 5 minutes.
- 原文没有具体数据时**不许编造**——改成泛指但具体的说法："还能更快"而非"有一定提升空间"。

## S6 去名词化

中文"进行 / 实施 / 做一个 + 名词"、英文"make / perform / carry out + noun"→ 直接用动词。

- 进行一次部署 → 部署；做出决定 → 决定；进行分析 → 分析
- make an adjustment → adjust；perform an analysis → analyze；carry out a review → review

## S7 术语一致性

同一概念全文同一个词。AI 常犯：前面"工作区"，后面"workspace"，再后面"空间"。

- 改写时建立术语表（脑内即可）：概念 → 选定词，全文统一
- 中英混排时专有名词首次出现给中英对照（"工作区（workspace）"），之后固定一种
- 不许为了"避免重复"而换同义词——技术写作里换词 = 换概念

## S8 连接词节制

"因此 / 然而 / 此外 / 而且 / 所以"每段开头都出现 → AI 的衔接拐杖。
能靠语序表达的逻辑关系就删连接词；一段最多保留一个。

- 前：此外，系统还支持插件机制。然而，插件需要单独安装。因此，我们建议…
- 后：系统支持插件机制，但插件需要单独安装。我们建议…

## S9 并列结构对齐

并列项语法结构一致：都是名词 / 都是动宾 / 都是完整句。

- 前：该工具支持格式化、代码检查，还能跑测试。→ 后：该工具支持格式化、代码检查和测试。
- 前：You can create, edit, and the deletion of documents. → 后：You can create, edit, and delete documents.
