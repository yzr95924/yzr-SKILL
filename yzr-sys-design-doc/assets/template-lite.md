# <功能名称>设计说明

> 元信息一行：状态（草稿）/ 作者 / 日期 / 评审人（无可省）

## 1. 背景与目标

现状一句话 + 改什么 + 目标（1–3 条）。小改动的背景超过半页 = 档位可能判错了，考虑转 full。
信息不足处以"假设："逐条列出，不一一向用户追问。

## 2. 方案设计

- 核心思路 + 关键流程；有状态流转时**必填状态机**（lite 档最常见的漏项）
- 数据变更：表 / 字段 / 缓存 key；没有写"无"
- 接口变更：新增 / 修改的 API；没有写"无"

## 3. 影响面

对现有功能 / 上下游 / 调用方的影响；兼容性判断。没有影响也要写"无"+ 一句依据
（如"仅新增字段，老接口行为不变"）——评审者要看到"考虑过"。

## 4. 回滚与预案

工程回退：上线后出问题怎么退（开关 / 回滚版本 / 修复脚本），一句话也要写。
与业务流程的"用户撤销"分开——那是 §2 的设计内容。

## 5. 自测要点

验收必须覆盖的 case 清单：至少 1 条正常路径 + 1 条异常路径。
