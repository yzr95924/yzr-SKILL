> **章节分层**：§1–5 **需求层**（不依赖实现：为什么做 / 做什么 / 做成什么样）→ §6–10 **方案层**

## 1. 背景与现状

写什么：现有系统 / 功能**现在怎么做的**（关键流程一段 + 必要的现状图）、痛点是什么
（量化：用数字不用形容词，数字标口径：实测 / 估算）、为什么现在做、相关上下文链接。
现状断言逐句给依据：代码位置 / 配置项 / 线上数据 / 用户口述；指不出依据的不写成事实——
以合理假设补齐，在本节末尾列**假设清单**（逐条编号），评审时逐条确认。

## 2. 目标与非目标

- **目标**：可验证（评审后能判"做到没"）；量化目标写"基线 → 目标值"，基线标口径（实测 / 估算）。
- **非目标**：本期明确不做的。写"不做什么"比写"做什么"更能防评审时范围蔓延。

## 3. 功能点拆解

写什么：把需求拆成可枚举的功能点清单（表格：编号 / 功能点 / 优先级 / 设计落点 → §7.x）。
为什么：这是"目标（为什么做）"到"方案（怎么做）"之间的 What 桥——评审者先确认"做哪些事"
没漏没偏，再看怎么做。配套自检：每个功能点在 §7 详细设计必须有落点；§7 里每个模块也应
能回溯到功能点——无落点的功能点 = 设计漏了，无功能点来源的设计 = 做了多余的事。
与 §4 的分工：本节是枚举粒度（有哪些事），规则细节归 §4。

## 4. 功能规格与约束

写什么：实现之后功能要遵守的**精确规则与硬约束**——这是需求层里最细的一档，换一套实现
依然成立：

- **功能规格**：每个功能点的规则口径——数值（冷静期 30 天、锁定 TTL 30 分钟）、上限
  （每类券最多 1 张、重提不限次）、默认策略（平局时按什么顺序仲裁、用户改选时尊重还是纠正）、
  边界行为（面额超出作用范围作废不退、驳回必须填理由）。
- **约束**：限制解空间的硬条件——技术约束（不引入新中间件 / 必须兼容现有单体）、
  业务约束（资损零容忍、对账差一分钱即告警）、合规约束（个人数据匿名化口径）。

为什么：目标是结果指标，功能点是枚举清单，但评审吵得最多的往往是**规则口径**
（"到底先扣哪张券"、"驳回要不要理由"）——规格节把这些一次性钉死，也是 §5 场景表
"期望行为"列的判定依据（场景引用规格，不重抄规则）。

## 5. 场景拆解

写什么：全量场景枚举表（场景 / 类型：主流程·分支·异常 / 触发条件 / 期望行为 / 设计落点）。
期望行为按 §4 规格判定，不在本表重抄规则细节。
为什么：全量设计的核心是"设计前先穷举"——这张表既是覆盖性自检（设计落点有空行 = 漏设计），
也是验收标准的来源（评审时直接当验收清单用）。异常场景在本节只写"会发生什么 + 期望行为"，
技术处置细节归 §8，两处用"设计落点"列互指，不重抄。

—— 方案层：怎么做（以下章节依赖实现决策）——

## 6. 方案总览

一段话核心思路 + 整体流程图 / 架构图（mermaid 或 ASCII 均可）+ 关键设计决策速览
（每条一句话，细节指向 §7 或 §10）。评审者 3 分钟读完这节应能复述你的方案。

## 7. 详细设计

### 7.1 流程与状态机

核心链路时序 + 状态流转。有状态流转的对象必填状态机（文字时序 / 状态机图），别只用文字描述。

### 7.2 数据设计

表结构变更（DDL 或字段表）/ 索引 / 存量数据迁移。改字段必须写清存量数据怎么办。

### 7.3 接口设计

新增 / 变更 API：路径、关键参数、错误码、幂等性、权限。接口语义变更（同一路径行为变了）
要显式标注——对调用方这是破坏性变更。

### 7.4 兼容与影响面

对现有流程 / 历史数据 / 上游下游 / 第三方调用方的影响。没有影响的维度写"无"+ 一句判断依据，
不许静默省略。

## 8. 异常与边界处置

写什么：§5 枚举出的异常场景的技术处置机制——并发竞争 / 幂等 / 超时 / 部分失败的设计细节。
与 §5 的分工：§5 说"会发生什么、期望什么行为"，本节说"技术上怎么做到"。最可能出线上事故的
3–5 条写透，不追求穷举（穷举已在 §5 做过）。

## 9. DFX 设计

非功能属性设计，五个子项**全部显式回应**：有内容写内容，不适用写"本期不适用 + 一句依据"——
评审要求的是"每项都考虑过"，不是每项都堆字。

### 9.1 性能与容量

有量化压力时写量级估算（QPS / 存储 / 延迟目标）+ 关键路径开销；内部低频功能注明
"量级低（日均 X），性能非主要矛盾"即可，不堆公式装样子。

### 9.2 可靠性

运行期故障的应对：依赖不可用的降级策略 / 限流 / 熔断 / 容灾。与 §12 回滚的区别：
回滚是"出问题退回去"，可靠性是"带着故障继续服务"。

### 9.3 安全与合规

鉴权 / 越权 / 注入 / 数据脱敏。涉及资金、个人敏感信息时必填实质内容；其余一句话带过。

### 9.4 可服务性

上线后的可运维性：关键监控指标（列指标名）/ 告警点 / 日志规范（trace 贯穿）/
常见运维操作（扩容、数据订正）的执行路径。

### 9.5 可测试性

设计上保证"可测"：依赖可打桩 / 内部状态可观测 / 时间与外部依赖可控制
（如测试后门：30 天冷静期可改成分钟级）/ 测试数据可构造。
本节是"可测性设计"，不是测试计划——测什么由 §5 场景表导出。

## 10. 备选方案与设计权衡

每个认真考虑过但被否的方案：方案一句话 + **为什么不选**（对照当前选择的取舍维度）。

—— 落地层：怎么拆解执行、怎么上线、何时交付 ——

## 11. 实施任务书（独立文件）

任务拆解不内嵌本文档——见独立文件 **`<功能slug>-tasks.md`**（按 `template-tasks.md` 生成）。
分工：本文档评审后保持稳定，执行状态 / 问题 / 设计变更都在任务书（活文档）里流转。
本节只需写：任务书文件路径 + 当前任务完成度一句话摘要（如"T1–T8 共 8 项，评审时全未开始"）。

## 12. 上线与回滚

- **上线**：灰度 / 开关 / 发布顺序（DDL 先行、前后端先后、数据迁移窗口）。
- **回滚**：出线上问题怎么退，具体到动作（切开关 / 回滚版本 / 数据修复脚本）。
  与"业务流程撤销"分开——那是 §7 的设计内容；这节只讲工程回退。

## 13. 开放问题

评审前未决事项清单：每条给默认倾向 + 待谁确认。没有未决项就写"无"——保留这节表明想过。

## 14. 排期（可选）

里程碑表格——里程碑 = 任务书（`<功能slug>-tasks.md`）中任务的分组 + 时间点，引用任务编号，
不重复任务内容。内部小项目 / 评审不关注排期时可省。
