# SFMEA 分析指导

[template-sfmea.md](../assets/template-sfmea.md) 只定义产物形状；SFMEA 文档的生成、更新、审计和复核按本文执行。

## 分析流程

1. 确定分析对象与范围，写明功能、分析边界及涉及的代码与测试范围，
   梳理功能流、子功能和输入。功能流是分析对象完成一项业务结果的端到端处理过程，
   可包含必要的上下游环节，不因代码可检索而扩展整个调用链
2. 从代码梳理当前子功能涉及的调用、资源、数据、消息、并发、共享状态、进程生命周期和外部依赖，记录相关配置与测试入口
3. 场景从梳理出的故障点导出：每个代码中可失败的操作，或对外部事件的具体暴露点，取其现实中可达的最简触发，
   不叠加多个独立故障或罕见前置条件；依赖或介质的内部故障（如存储介质静默损坏、网络丢包）
   在形态未确认时按“条件适用”处理，不写完整行；进程复位、掉电、时间跳变等系统级事件不受此限。
   故障库条目本身即复合故障的按条目原样分析；故障库用于为故障点命名并校验是否漏掉适用类别，不因库条目存在而虚构场景
4. 以每个子功能为对象逐类检查故障模式库，按对应对象、依赖和作用路径判断适用性；
   不因代码没有显式故障路径跳过判断，数据与配置访问、系统环境类必须逐项判断。
   一行描述一个子功能在一组输入下的一种故障模式。同一行只对应一种最终结果：
   最终状态、功能结果或恢复方式不同的输入场景拆行，相同的合并，不按异常类型逐个拆行
5. 对每个直接适用故障模式沿传播路径检查处理措施和影响，阅读用例正文核实覆盖
6. 按模板补齐字段，复核遗漏、重复和证据状态

## 成文要求

- 功能流表用业务对象、动作和状态表达，保留必要接口名，只写结论；不写调用链、行号、
  代码执行顺序、完整异常传播和分支推导
- 超过两句话时复核是否混入推导或重复；精确优先于简短，保留故障对象、执行主体、
  关键条件、参数和结果
- 不使用未指明对象的“下游响应慢”“服务异常”“存储失败”等泛称；对象未知时写“具体组件待确认”
- 只把至少两行复用的触发条件和代码事实写在表格前，不写代码走读

## 功能流章节

- 子功能是分析对象实现过程中的一个处理环节或子能力，作为三级标题说明故障发生在哪个处理过程
- 粒度根据实际功能灵活划分，不要求与代码函数、类或模块一一对应
- 同一功能流内尽量保持相近粒度，同一处理过程使用同一个子功能名称
- 划分到能够定位故障并区分后续字段结论即可；不同处理过程的结论明显不同时再拆分
- 每次只写一个子功能分组并交用户确认，确认后再写下一组，不一次写完整个功能流
- 全部子功能分组确认后，再单独输出“条件适用项”三级小节；没有条件适用项时省略
- 该小节列出故障模式、待确认条件和可能影响，不生成完整行；确认后再补入主表

## 表达示例

材料已确认下游为 `notification-gateway` 时：

- 原因：`notification-gateway` 响应超过 Sender 超时时间；可能：两者间链路拥塞
- 已有措施：Sender 超时 1 秒；`send_batch` 最多尝试 3 次
- 影响：当前通知失败，其余通知继续；重试可能使 `notification-gateway` 重复投递
- 注入方法：建议：让 `FakeSender.send` 连续抛出 `TimeoutError`

下游对象未确认时写“Sender 对端服务响应超时，具体服务待确认”，不虚构组件名。

“配置缺失或非法”的输入导致不同最终结果时拆行，例如：

- `retry_times` 缺失或类型错误：处理中断，不执行 `repo.save`，通知状态不变
- `retry_times` 为 0 或负数：不发送，全部置 `failed` 并回写

文件缺失、无权限和 JSON 非法最终结果相同，合并一行，原因写“路径错误、权限不足或 JSON 内容非法”。

## 字段定义

### 输入

描述该子处理过程所需的前提条件，包括应用场景、用户操作、输入参数和相关前置状态。

- 只写理解和分析该故障所需的关键前提，不抄全量参数与环境信息
- 只写该故障点最简触发所需的前提；传播过程写在“影响”，不预置为输入
- 前置条件须有代码、配置或已确认部署事实支撑，不虚构部署形态或调用组合；未确认的按“条件适用”处理
- 子处理过程的前提条件写在“输入”，故障如何制造写在“注入方法”

### 故障模式

故障模式库见 [sfmea-failure-modes.md](../assets/sfmea-failure-modes.md)。

故障模式填写故障模式库中适用于当前子功能的条目名称，保持原文；具体对象和场景由三级标题“子功能”与“输入”表达。

- 读取完整故障模式库，以每个子功能为对象逐项判断适用性
- 直接适用：代码路径存在对应对象或依赖，或系统级事件能够直接中断、破坏当前处理；不受已有措施和测试覆盖影响
- 条件适用：对应对象、依赖或故障作用路径只在特定部署、协议或实现形态下存在，且材料未确认该形态；
  不生成完整行，改为列出待确认条件和可能影响
- 不适用：没有对应对象或依赖，故障也不能通过依赖链影响当前子功能；不生成行、不说明原因，也不再分析后续字段
- 外部事件和硬件故障作为假设条件判断，不要求代码中已经出现该故障；代码用于确认传播路径、现有措施和影响
- 依赖实现未提供时，可以分析接口边界的超时、返回失败和读写失败；不臆造吞异常、缓冲未刷盘、事务未提交等内部机制，未确认写“待确认”
- 直接适用条目一项一行，名称不改写、不拼接场景，不混入原因或影响
- 同一故障涉及多个层级时，只在“故障模式”填写最直接的一层；外部事件或硬件异常写入“原因”，不重复生成行
- 同一库条目包含多个并列故障模式时，按具体模式拆行，名称沿用库中原词
- 无法判断属于直接适用还是条件适用时，先补查代码和材料；仍无法确定则列为条件适用并集中向用户确认，不能按不适用静默跳过
- 故障模式库未覆盖时，先确认是否补充故障模式库，不临时造名称

### 原因

导致该故障模式的可能原因，用于有针对性地提出改进建议。故障模式库的说明可提供典型原因线索，不能替代当前场景分析。

- 结合子功能、输入、代码、配置与外部依赖判断，不机械复制故障模式库中的通用说明
- 已确认的原因直接写，有依据但未确认的标“可能：”，无法确定写“待确认”
- 分析到能支撑针对性改进即可，不穷举理论可能，也不把已有措施不足写成原因

### 已有措施

系统为降低该故障影响已经采取的容错、规避和恢复措施；能够发现该故障或其影响的日志、监控和告警可作为检测手段一并列出，但不代表具备恢复能力。

- 沿当前子功能的代码与配置核实措施，共享机制只有确认对当前流程生效才写入
- 按实际能力和执行主体描述，保留重试次数、超时时间等关键参数
- 不写改进想法；确认没有措施写“无”，无法确认写“待确认”

### 影响

该故障模式对功能实现造成的影响；有措施时写措施处理后的影响，无措施时写故障的直接影响。

- 写清哪个对象受到什么影响：故障期间及最终的功能结果，如是否完成、是否部分成功、
  最终状态和数据是否正确；有调用方或用户可观察表现时一并说明
- 不重复故障模式和已有措施，不写“影响可靠性”等泛化描述
- 有证据表明影响被消除时才写“无影响”；推断注明依据和验证方式，无法确定写“待确认”

### UT/ST 覆盖

验证该故障模式及其处理结果的现有 UT/ST 用例。UT/ST 的验证范围与测试报告写作指导中的[章节](test-report.md#表格填写)一致。

- 有用例写用例名，多个用分号分隔；没有写“未覆盖”，无法判断写“待确认”
- 不能只按用例名判断覆盖，必须确认用例实际构造或注入该故障，并验证处理结果
- “未覆盖”和“待确认”单独填写，不附推测说明；只记录覆盖情况，不写执行结果

### 改进建议

用于提高可靠性、减少该故障模式影响的改进方法。

- 结合当前场景提出，可涉及容错、规避、恢复、检测或测试验证，不预设固定方案；建议应有针对性，不写空话
- 不要求每行提出新方案；没有合理建议写“无”，无法判断写“待确认”

### 恢复步骤与时间

从该故障发生到功能恢复的处理步骤及所需时间，用于测试样例验收。

- 根据代码与配置梳理恢复执行主体、对象，以及故障检测、重试或切换、状态恢复、
  功能恢复确认等步骤，只写实际存在或有材料依据的机制
- 时间注明来自配置推导、设计预期还是实测；不能把单次重试间隔或进程启动时间当作总恢复时间。没有依据时写“时间待确认”，不推测可能依赖的外部因素
- 没有恢复机制写“无”，只有人工恢复时写明人工步骤，不留空、不编造

### 注入方法

为复现该故障模式，在测试中制造对应故障的操作方式，用于测试样例验收。

- 写清注入对象、故障动作和触发条件，不限定测试层级
- 只写如何制造故障，不写完整测试流程、预期结果或断言
- UT/ST 场景结合代码与用例，已有用例按实际方法填写，新提出的方法标“建议：”，无法确定写“待确认”
- E2E 只在材料已经提供时按实际方法转写，没有材料时不展开设计，写“待确认”

## 交付前复核

- 直接适用项都在主表且没有重复，条件适用项单独列出，不适用项没有生成行
- 措施和影响有代码、配置或用例依据，推断与待确认标注正确
- 表格用结论化表达，共享事实已写在表格前，没有重复代码推理或用例内容
- 每个子功能都有独立三级标题和九列表格，UT/ST 覆盖来自实际构造故障的用例，恢复与注入信息没有编造
