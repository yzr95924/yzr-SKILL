# SFMEA 分析指导

[template-sfmea.md](../assets/template-sfmea.md) 只定义产物形状；SFMEA 文档的生成、更新、审计和复核按本文执行。

## 分析流程

1. 确定分析对象与范围，梳理功能流、子功能和输入。功能流是分析对象完成一项业务结果的端到端处理过程
2. 以每个子功能为对象逐项检查故障模式库，跳过不适用项。一行描述一个子功能在一组输入下的一种故障模式；输入或后续结论无法共用时拆行
3. 对每个适用故障模式结合代码、配置和用例补齐后续字段，按模板成文

## 字段定义

### 子功能

分析对象实现过程中的一个处理环节或子能力，用于说明故障发生在哪个处理过程中。

- 粒度根据实际功能灵活划分，不要求与代码函数、类或模块一一对应
- 同一功能流内尽量保持相近粒度，同一处理过程使用同一个子功能名称
- 划分到能够定位故障并区分后续字段结论即可；不同处理过程的结论明显不同时再拆分

### 输入

描述该子处理过程所需的前提条件，包括应用场景、用户操作、输入参数和相关前置状态。

- 只写理解和分析该故障所需的关键前提，不抄全量参数与环境信息
- 子处理过程的前提条件写在“输入”，故障如何制造写在“注入方法”

### 故障模式

故障模式库见 [sfmea-failure-modes.md](../assets/sfmea-failure-modes.md)。

故障模式填写故障模式库中适用于当前子功能的条目名称，保持原文；具体对象和场景由“子功能”与“输入”表达。

- 读取完整故障模式库，以每个子功能为对象逐项判断适用性；适用性只看是否具备故障发生条件，不受已有措施和测试覆盖影响
- 适用条目一项一行，名称不改写、不拼接场景，不混入原因或影响
- 同一库条目包含多个并列故障模式时，按具体模式拆行，名称沿用库中原词
- 明确不适用的条目直接跳过，不生成行、不说明原因，也不再分析后续字段
- 无法判断是否适用时先补查代码和材料，仍无法确定则集中向用户确认，不能按不适用静默跳过
- 故障模式库未覆盖时，先确认是否补充故障模式库，不临时造名称

### 原因

导致该故障模式的可能原因，用于有针对性地提出改进建议。故障模式库的说明可提供典型原因线索，不能替代当前场景分析。

- 结合子功能、输入、代码、配置与外部依赖判断，不机械复制故障模式库中的通用说明
- 已确认的原因直接写，有依据但未确认的标“可能：”，无法确定写“待确认”
- 分析到能支撑针对性改进即可，不穷举理论可能，也不把已有措施不足写成原因

### 已有措施

系统为降低该故障影响已经采取的容错、规避和恢复措施；能够发现该故障或其影响的日志、监控和告警可作为检测手段一并列出，但不代表具备恢复能力。

- 沿当前子功能的代码与配置核实措施，共享机制只有确认对当前流程生效才写入
- 按实际能力描述，保留重试次数、超时时间等关键参数
- 不写改进想法；确认没有措施写“无”，无法确认写“待确认”

### 影响

该故障模式对功能实现造成的影响；有措施时写措施处理后的影响，无措施时写故障的直接影响。

- 写故障期间及最终的功能结果，如是否完成、是否部分成功、最终状态和数据是否正确；有调用方或用户可观察表现时一并说明
- 不重复故障模式和已有措施，不写“影响可靠性”等泛化描述
- 有证据表明影响被消除时才写“无影响”；推断注明依据和验证方式，无法确定写“待确认”

### UT/ST 覆盖

验证该故障模式及其处理结果的现有 UT/ST 用例。UT/ST 的验证范围与测试报告写作指导中的[章节](test-report.md#表格填写)一致。

- 有用例写用例名，多个用分号分隔；没有写“未覆盖”，无法判断写“待确认”
- 只覆盖正常流程、未构造或注入该故障的用例不算覆盖
- 只记录覆盖情况，不写执行结果；“未覆盖”仅指没有 UT/ST 用例

### 改进建议

用于提高可靠性、减少该故障模式影响的改进方法。

- 结合当前场景提出，可涉及容错、规避、恢复、检测或测试验证，不预设固定方案；建议应有针对性，不写空话
- 不要求每行提出新方案；没有合理建议写“无”，无法判断写“待确认”

### 恢复步骤与时间

从该故障发生到功能恢复的处理步骤及所需时间，用于测试样例验收。

- 根据代码与配置梳理故障检测、重试或切换、状态恢复、功能恢复确认等步骤，只写实际存在或有材料依据的机制
- 时间注明来自配置推导、设计预期还是实测；不能把单次重试间隔或进程启动时间当作总恢复时间，无法确定写“待确认”
- 没有恢复机制写“无”，只有人工恢复时写明人工步骤，不留空、不编造

### 注入方法

为复现该故障模式，在测试中制造对应故障的操作方式，用于测试样例验收。

- 写清注入对象、故障动作和触发条件，不限定测试层级
- UT/ST 场景结合代码与用例，已有用例按实际方法填写，新提出的方法标“建议：”，无法确定写“待确认”
- E2E 只在材料已经提供时按实际方法转写，没有材料时不展开设计，写“待确认”
