# 测试报告写作指导

[template-test.md](../assets/template-test.md) 只定义产物形状；测试报告的生成、更新、审计和复核按本文执行。

代码 commit ID、分支和构建号默认不写，用户明确要求时再补。

## 测试范围

- 测试结果按状态填写：PASS 已执行且符合预期；FAIL 已执行但不符合预期；
  BLOCKED 因阻塞无法执行；SKIP 本次改动不涉及，不需要测试；材料未提供结果写“待确认”
- 测试结果按用户材料转写，不按用例明细自行汇总；材料只给用例结果而未给测试项结果时先问用户
- SKIP 原因写在汇总表后，一行一条：`SKIP：<测试项>，<原因>`；无 SKIP 时不写

## 测试类型

- 按验证对象和目标归纳测试项，并据此选择测试类型；故障注入按注入位置区分白盒和黑盒
- 工具、执行环境和用例类型不单独决定测试类型
- 功能测试：验证功能行为、计算结果和状态变化是否符合预期；同一功能用例的 ASAN、LSAN 执行
  作为附加证据，不改变测试类型
- 性能测试：测量或验证时延、吞吐、CPU 消耗等计算效率指标
- 内存开销测试：测量或验证峰值内存、稳态内存、单对象开销及优化前后的内存变化
- 白盒故障注入：在代码或组件内部自设故障注入点，使指定调用失败、超时或返回异常，
  验证对应处理逻辑
- 黑盒故障注入：从系统外部制造断网、进程退出、依赖服务不可用等故障，
  验证故障下的系统对外行为和处理结果
- 升级测试：验证版本切换、数据迁移和回滚是否符合预期
- 兼容性测试：验证不同版本、平台、协议或数据格式能否共同工作
- 仅测试类型、测试项、用例类型和测试结果均相同的多次执行合并到一行，测试详情写清各次证据
- 现有类型无法准确表达验证内容时可新增

## 章节路由

- 至少一行测试结果非 SKIP 的测试项生成一个二级章节，标题与“测试项”一致
- 所有行的测试结果均为 SKIP 的测试项不生成二级章节，原因只写在汇总表后
- 同一测试项有多种用例类型时，合并在同一个二级章节
- UT / FT / ST：只保留对应用例小节和表格
- 自行设计的 E2E：保留测试环境信息、操作步骤、预期观察点、运行结果
- 已有每日回归 E2E：保留测试环境信息、预期观察点、运行结果，不写操作步骤

## 表格填写

- 使用 gtest 时，类别和用例名分别对应 TestSuiteName 和 TestName，与代码保持一致
- 多个用例共享 Fixture SetUp、测试数据或测试代码时，在表格前写共享说明
- 参数化用例写明具体参数；UT 写在场景中，FT / ST 写在测试流程中
- UT 使用 gtest 覆盖函数、类或模块内部逻辑，隔离外部依赖
- ST 直接运行测试二进制，在单进程内验证进程行为；被测进程、模拟实体或角色、
  代码 mock 与共享前置写在表格前
- FT 用 Docker 启动真实业务二进制验证系统集成，不使用代码级 mock；参与组件、
  环境 mock 与共享前置写在表格前，公共容器拓扑和关键配置放测试详情或表格前
- UT 的场景写前置条件、输入或触发条件；主要检查点写重点验证的结果、状态或行为；
  验证逻辑简述构造、执行和断言方式，不复制完整测试代码
- FT / ST 的测试流程按执行顺序写清操作对象、输入和动作；
  表格内只写简短流程，完整或共享流程放测试详情或表格前
- 预期结果写可观察、可判定的行为；个别用例禁用或未执行时写明用例与原因，
  不把整测试项改成 SKIP，除非用户说明该测试项不涉及

## E2E 小节

- 测试环境信息：自行设计的用例写部署环境、关键配置、依赖和数据准备；
  已有每日回归任务写任务名称、ID 或链接、绑定环境及关键配置
- 操作步骤：按执行顺序编号，写清每步入口、操作、输入和配置
- 预期观察点：写执行期间需要观察的日志，必要时补充指标、trace 和数据状态；
  每项注明名称或位置、关注字段或事件，以及异常判据
- 运行结果：写本次实际运行结果，优先附执行记录链接或截图；
  E2E 从真实用户入口覆盖完整业务链路，在独立平台执行时优先放平台执行记录链接；
  截图附简要说明，指出需要关注的内容

## 遗留问题与结论

- 遗留问题写失败现象、阻塞项和影响；原因已确认时才写，未确认写待确认；没有写“无”
- 存在非 SKIP 测试项且其测试结果均为 PASS 时才可写整体通过；存在 FAIL、BLOCKED 或待确认时，
  在结论中说明影响，不写整体通过
- 交付前核对汇总表、正文章节和运行证据一致
